  - `isHidden(): boolean` (RAC `useIsHidden`: true in build mode — Popover etc. must render their children directly when `isHidden()`, register-only, like RAC `Hidden`)
  - `CollectionRendererContext` / `DefaultCollectionRenderer` / `CollectionRenderer { isVirtualized?, layoutDelegate?, dropTargetDelegate?, CollectionRoot(props: CollectionRootProps), CollectionBranch(props: CollectionBranchProps) }`; `CollectionRootProps { collection: Collection | null; content?; idScope?; persistedKeys?; focusedKey? (Rivet: accessor, virtualizers persist it); scrollRef?; renderDropIndicator? }`; `CollectionRenderer.onScroll?` (Rivet: hosts forward their scroller's `scroll` events; virtualizer renderer) (collection null = live mode: render `content` in place); `CollectionBranchProps { collection | null; parent; renderDropIndicator? }`
  - `collectionItemId()`: the id a part rendered for a `Collection items` row gets (row default, consumed like `takeItemDefaults`; hideable parts that are not leaves, e.g. `TabPanel`)
  - `renderNodeAt(collection, key)`, `sameRender(a, b)` (see Build-pass tracking below); `serverRows(collection, keys, parentType?)` / `resumedKeys(collection, base, keys)` (resumed rows, below); node class `static liveProps?: readonly string[]` (`base.ts` `CollectionNodeClass`)
  - `CollectionScopeContext` (`rv-collection-scope`, `{ parentKey, level, idScope? }`), `SectionContext` (`{ name, render(props, ref, section, className?) }`), `Section` (deprecated upstream), `persistedKeys(focusedKey)`, types `ItemRenderProps`, `SectionProps`, `CollectionProps`, `CollectionPartProps`, `CollectionNodeClass`, `CollectionNodeSpec`
  - Two modes: LIVE (default; parts render real DOM in place with `data-key`, state reads `domCollection(root)` per event; `node` has key/type/value/textValue/props/level/parentKey only, no sibling links) and BUILD (`collectionOf` / `CollectionBuilder`: content runs with parts registering `CollectionNodeSpec` + `render` thunk, committed by `buildCollection` into a frozen `BaseCollection`; a host renders from it with `CollectionRoot({ collection })` → `node.render(node)` per node, `type === "content"` nodes skipped — Tree / Table flattened rows). Build runs inside a `computed`: signal reads in the content rebuild it; a handler capturing the accessor rebuilds it in the browser from its recipe.
  - Never capture `node` / a collection / a `SelectionManager` in a resumable closure — capture keys and the serializable state.
  - Ids: explicit `id` > `Collection items` default (`item.id ?? item.key`) > generated `$.n` (`<parentKey>.$.n` nested). Only the FIRST part a row renders takes the row's id / value (RAC `addIdAndValue` clones one element; `takeItemDefaults`, WeakSet outside the serialized context): a fragment's other parts (trailing load-more item) keep their own / auto ids. Built-node renders and branch `useChildren` get `id` only when explicit / item default, never a generated key (RAC passes `node.props` as given; Table's static-row id check relies on it).
  - `textValue` default: string / number children only, else "" — lazy slot children are NEVER evaluated for it (would render content twice); give `textValue` for non-string children.
  - `collectionChildren`: `items` + item renderer → one part per item; `items == null` with an item renderer (function child, arity ≥ 1, not a slot) → nothing; a 0-arity function child is content.
  - Live placement (`place()` in `components.tsx`): content rendered in place inside the collection providers (CollectionRoot live mode, branch `content`, `Collection`, item rows) runs slots now, but keeps any other 0-arity function — a `{() => …}` child or a DOM accessor (`<For>` / `<Show>` / dynamic fragment child) — as a reactive child read through reactivity `_scoped` (fresh scope under the placing owner per read: context lookups still see the providers). Never call such a function once to "evaluate" live content: the rows / filtered options would never update (`libs/compiler/tests/dom-rows.test.ts`). Build mode (`evaluate`) still calls everything, tracked by the build; server: `evaluate`.
  - Live `Collection items`: rows keyed by `itemId`; a row reads `item()` and re-renders reactively (returns a function, not a fragment: `<>{x}</>` compiles to an array). `renderNodes` (built) keys `For` by primitive keys and resolves the node untracked.
  - Build pass: `buildCollectionFrom` runs under `_rUnrecorded` (runtime keeps `_rFn` closure registration there, so build-pass slots / render fns resume) inside `HiddenContext`.
  - Build-pass tracking (F3): component bodies run untracked (runtime component creation), so the build captures its observer (`_observer()` from `@rivetjs/reactivity`, on `BuildScope.run`, cleared when the build ends) and parts re-enter it (`tracked(build, fn)` = `_reobserve`) before evaluating user content: branch `useChildren`, `Collection` / `collectionChildren` (`items` accessors / signals, item renderers), `CollectionBuilder` content. A signal read there rebuilds the collection (RAC: React re-renders the hidden tree). Reads in component *props* expressions (`<Column width={w()}>`) stay snapshots (same as live mode); explicit `untrack` stays untracked; Popover / Tooltip hidden-branch slot reads are not re-entered (their ListBox / Collection children are).
  - Rendering built nodes: `renderNodeAt(collection: () => C, key: () => Key): () => unknown` — per-row `computed(getItem(key), { equals: sameRender })` + dynamic region rendering `node.render(node)` untracked: an unchanged node keeps its rendered part (DOM element, focus) across rebuilds, a node whose render inputs changed re-renders. Server: renders the node once, untracked (`computed` / `depends` are browser re-render triggers; read in a resumable row they flagged it as reading signals, so the resumed `For` re-created the table header / body on every region re-run — focus lost after a sort, cdk-docs `table-tailwind`; `tests-components/table.test.ts`). Used by `renderNodes` (`CollectionRoot` / `CollectionBranch`), Table header row cells, Tree content rows. `key` may be a `RowBox` (`rowKey(key())`, resumed rows below). `sameRender(a, b)`: same class / key / textValue / aria-label, `rendered` + shallow `props` + shallow plain-object `value` equal; functions equal when identical or same source (`String(fn)`, slot brand, arity: closures re-created by a rebuild); sibling links / index / level ignored (parts read them live by key); node class `static liveProps` (e.g. `TableColumnNode` widths) skipped in props / value.
  - Lazy rows (LAZY-ROWS T3 2026-10-19): `renderNodes` / `collectionChildren` / Table / Tree / virtualizer Fors are keyed `For`s with an inline row arrow (`(key) => renderNodeAt(…)`): compiler lazy-row verdict `eligible` (40 / 43 cdk Fors; ineligible: carousel `by` + `capture`, scrolling/viewport `capture` — not collections). Keep it that way: no spread, no function `by` beyond `(key) => key`, no non-serializable capture in the row arrow. Hosts on built collections: ListBox, GridList, Table, Tree, Select / ComboBox, virtualizers; live: Menu, TagGroup, Tabs. Lazy one level down (LAZY-T6): `renderNodes` passes `lazy={() => leafNodes(collection, parent)}` (false when a node is a section or has child nodes — Table root parts, sectioned ListBox, Tree parents), so the leaf row For is the lazy one and a "row" never spans a nested collection. Server cost (LAZY-COST-2 2026-10-21): a `renderNodeAt` row value holds nothing left to run (compiled / attribute / spread records, text: runtime `server-resume.ts` `writable`), so lazy rows of every cdk collection render to HTML 32 rows per renderer, not one `renderToString` per row; keep row values free of function children / lazy slots that run at traversal (such a row falls back to its own renderer). `leafNodes` skips a node with `firstChildKey === null` without walking `childNodes` (1000 options ≈ 0.5 ms per render before).
  - A built collection captured by a resumable closure: create it in the component body as `const c = computed(() => buildCollectionFrom(() => Collection({...}), () => new XCollection()))` (compiler emits `_rComputed`); a `collectionOf()` accessor captured by a closure is rejected by the encoder. Capture `DefaultCollectionRenderer` methods via a null check (`const custom = renderer === DefaultCollectionRenderer ? null : renderer`), never the module object's methods.

## Rules / invariants
- Never capture a `ListCollection` / `SelectionManager` instance in a resumable closure; capture the serializable state, rebuild per event (`listSelectionManager(state)`)
- `SelectionModel` is client-only; resumable component selection = `../selection/state.ts` signals
- `index.ts` keys compare as strings (`sameKey`): `data-key` is a string, state keys may be numbers
- `dom.ts` node mapping (header comment `dom.ts:1-15`): key `data-key` (+ `data-key-type="number"`), type `data-type` else by role, text `data-text-value` / `data-text` / `aria-label` / textContent, `[hidden]` subtrees skipped
- Two different `Selection` types: `index.ts` (Rivet object) vs `types.ts` (`"all" | Set<Key>`); `list-state.ts` imports the former as `LegacySelection`
- live props (P5): part node props (`nodeProps`, leaves + branches, build pass + live mode) forward unread when a prop is live (runtime `splitProps`): the build pass does not depend on a live prop (no node rebuild / row re-creation), `node.props.isDisabled` / `class` stay live for the selection manager and the part. Specs from parts set `ownProps` (`base.ts` `buildCollection` uses `spec.props` without the `{ ...props }` copy, which read every getter in the tracked build pass and re-rendered Tree / Table rows on a live `class`). Render props (`withNode`): live without an `items` row → the part's own props (no merge); with one → `mergeProps(node.props, { id, value })`; static → `{ ...node.props, id, value }`. Branch children stay in the node props

## Gotchas
- `types.ts` is THE home of the shared @react-types/shared types (`Key`, `Selection`, `SelectionMode` incl. `"none"`, `SelectionBehavior`, `FocusStrategy`, `DisabledBehavior`, `Orientation`, `Direction`): `index.ts`, `../_adapters/*`, `../bidi`, `../i18n`, `../scrolling/state.ts`, `../virtualizer/types.ts` re-export them. `index.ts` `Selection` (interface, `createSelection` state) still shadows `types.ts` `Selection` (`"all" | Set<Key>`) under the same name — rename in the API phase.
- Plain JSX children of collection components arrive as a compiler slot: `forEachChild` resolves it, the item-renderer checks are `typeof children === "function" && !isSlot(children)` (`builder.ts`, `table.ts`, `list-state.ts`).
- ListBox (and color-swatch-picker, combobox, select via ListBox) runs on `list-state.ts` + `../selection/*`; `listbox/options.tsx`, menu, tabs, toolbar, breadcrumbs still use `../_adapters/` (`state/list.ts` is the adapter-based list state)
- Build-pass order (LAZY-ROWS T3 2026-10-19, before: dynamic children registered after their siblings): a dynamic `{() => …}` / `<Show>` / `<For>` child registers when `evaluate` calls it, AFTER the eager JSX siblings of the same children list (JSX builds the array, calling the sibling components, first). Browser builds put it back in document order: parts return a build mark (`buildMark(spec)`: an empty comment node, WeakMap → spec; renders nothing; a node, not an array, since the dev runtime copies component output arrays) instead of `null`, and `evaluate` on an array holding an accessor (`hasThunk`) runs `evaluateInOrder` (each mark = its spec's slot, each accessor = the specs it pushed; the list tail is rewritten in that order). Server: `null` (the server build sees dynamic children as values, already in order). `tests/collection-build.browser.test.tsx` pins it (root + nested, middle position).
- `<Show>` in built collection children on a resumed page (open gap, runtime): the server `Show` renders its branch in its own root (`server-structural.ts` `scoped` → `createRoot`, untracked), so the build's computed does not depend on `when` and the collection's `For` records no dependency: the row never appears after resume. Write `{cond() && <Item/>}` (tracked by the build); client renders are fine. Fix belongs in the runtime (server Show inside a build pass tracking `when`).
- Rebuild cost: a tracked change re-runs the whole build (O(items), like RAC's hidden render); measured 1000 `Collection items` rows: build ≈ 2.0 ms either way (re-entry overhead in the noise), mount 8.3–9.0 → 8.6–10.1 ms (`renderNodeAt` computed + region per row), rotate + change one row ≈ 13 ms with one row re-rendered.
- Hosts create `CollectionRoot` / `renderNodes` inside a JSX child region (`<Provider values=…>{renderer.CollectionRoot(…)}</Provider>`), never in the component body: a `For` created in the body reads its `each` (the collection) in the host's enclosing region, so a resumed page re-creates the whole host on the first collection change (fresh state; adopted rows keep bindings to the server state). ListBox fixed CDK-EX 2026-10-20 (`../listbox/CLAUDE.md`).
- Resumed rows (ROW-RERENDER 2026-10-20; OPEN since CDK-EX): adopted server rows of a keyed `For` over collection keys are kept by key and never re-run (server rendered them untracked; the `sameRender` cut-off exists only for browser-created rows), so a node value change (`createListData.update`, cdk-docs `data-list`) left the server text. Fix = per-row server stamp + browser re-check, cdk only (no runtime change):
  - `row-stamps.ts`: `stamp(node, children?)` = 24-bit FNV hash of what `sameRender` compares (`type`, key incl. number vs string, `textValue`, `aria-label`, `rendered`, props, value; liveProps skipped; functions / class instances by kind only — server and browser compile them differently; nested data to depth 2–3, ≤ 256 values per node), 4 chars of `[A-Za-z0-9_-]`; `stampSet(base)`; `RowBox` / `rowKey`.
  - `serverRows(collection, keys, parentType?)` (server and browser, same call site): one `_regionState` slot when `collection` is an accessor — server value = the stamps of the rows it renders (concatenated, set semantics; key is in the hash) when the build read signals (`_trackReads`), else null; browser fresh render: null; browser region re-creation: the server's value back (the For adopting the rows is in the same region read: call it there, never in an outer component body — `VirtualizerRoot`'s For sits in its own `_rBind` site, hence `viewRows`). No slot (null) for the children of a `section` / table row (`parentType` "section" / "item": static, positional slot) — the outer row's stamp covers them (`rowNodes`: a section's items, a row's `cell`s).
  - `resumedKeys(collection, base, keys)`: browser + baseline only (else `keys` itself): per pass, a key whose row nodes (`rowNodes`) differ from the last ones checked (`sameRender` node by node) is stamped; stamp in the set → kept (nodes remembered), else boxed for good (`{ k }`, one box per key) — a For key the adopted list does not know, so `_for` drops the server row and creates a browser row (`renderNodeAt(…, key)` unboxes, `rowKey`). Server keys / bytes of `$lazy` items unchanged (the server never boxes). Works with and without `resume.lazyRows` (kept lazy rows are adopted rows too).
  - Users: `renderNodes` (ListBox / GridList / Table root + body / Tree / Select / ComboBox), virtualizer `viewRows`. Not: Breadcrumbs' own For, Table header-row cells For, Tree content-rows For (items = values: re-created by `_for`'s own item check).
  - Granularity: the changed row only; a `ListBoxSection` (rows' For built in its body, no region of its own) / a table row (cells) is re-created as a whole when an item / cell changes. A `<TableBody items={array}>` (not an accessor) changes the body node's props: the whole body re-renders, resumed or not (same as a client render).
  - Cost (2026-10-20, story bench 1000-row createListData ListBox + 1000-row Table, `items` accessors): state +8,053 B raw (4 B / row) / +6.8 KB br eager, +8,050 B / +5.7 KB br with lazy rows (13.2 → 18.9 KB br); static collections 0 B (`/listbox` state identical). Browser (ScriptDuration, 5 runs): first update after resume list 7 → 10 ms, table 59 → 64 ms (HEAD stale); next update list 3 → 3.5 ms, table 21 → 26 ms (per-pass `sameRender` of every adopted row + cells, as a client row's cut-off computed does).
