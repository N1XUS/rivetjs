# @rivetjs/motion benchmarks (lane MOTION, 2026-10-12)

Spec `docs/design/specs/2026-10-11-motion-design.md`, plan `docs/design/plans/2026-10-11-motion.md`. Sections land per plan task. T14 = the motion suite in `apps/dom-bench/motion/` (rivet / React 19 + `motion/react` / vanilla `motion`); raw numbers in `2026-10-12-motion.json`.

## Layout drivers (D12, T12)

- Scenario: cdk `Masonry`, 1000 items (aspect ratios known: server-placed geometry), 6 columns, 1200 px; one relayout = item 0 expands to span 2 (every later item moves). Chromium (Playwright), 4× CPU throttle, fresh page per sample, lanes interleaved.
- Lanes: `house` = `motion` on (cdk `motion1dDriver`, Motion1D), `waapi` = `motion={layoutDriver({ duration: 0.4 })}` (`@rivetjs/motion/layout`), `motion` = `motion={false}` + Motion 14.1 `animateLayout(grid, update, { duration: 0.4 })` over the same items (`data-layout`).
- Metrics: `first` = trigger → first rAF (ms); `dropped` = rAF intervals > 25 ms in 700 ms; `reads` = `getBoundingClientRect` / `offset*` calls; `script` / `layouts` / `task` = CDP `ScriptDuration` (ms), `LayoutCount`, `TaskDuration` (ms) deltas over the window.
- Harness: `$S/motion/flip-ab/` (`page.tsx`, `build.mjs` rolldown + Rivet compiler, `run.mjs`), not committed.

| lane | first ms | dropped | reads | script ms | layouts | task ms |
| --- | --- | --- | --- | --- | --- | --- |
| house (Motion1D) | 37.1 | 1 | 1 | 10.7 | 42 | 185.9 |
| waapi (`layoutDriver`) | 35.9 | 1 | 1 | 10.5 | 25 | 135.8 |
| Motion `animateLayout` | 112.0 | 5 | 2000 | 259.1 | 3 | 523.8 |

- n = 1 (smoke run, host load ≈ 5). The timed run (7 interleaved samples under the bench lock) was parked: host 1-min load stayed 20–27 for > 20 min (other lanes). Rerun with T14.
- Reading: the shared FLIP core reads 1 rect (the grid; boxes come from the pure geometry) vs 2 per item for Motion's projection; Motion's engine costs 24× the scripting and 3× the time to first frame. Its `layouts` count is low because it batches reads into one forced layout, but the reads themselves dominate. Bytes: Motion's `animateLayout` 27.1 KB br (T1 spike) vs `layoutDriver` 3.2 KB br incl. mini `animate` (cdk FLIP core shared with masonry).
- Verdict: D12 stays (one cdk FLIP core, Motion1D default, `layoutDriver` opt-in); Motion's `animateLayout` wins no metric.

## List entrance, CSS vs JS (D9 cross-check, T12 step 3a)

- Scenario: client render of 1000 `<li>` with an entrance (opacity 0 → 1, y 20 → 0, 0.4 s). Lanes: `css` = `<Motion.li initial animate>` (CSS `@keyframes` via the constructable sheet, D9), `js` = plain `<li>` + `motion/mini` `animate` per element on mount. Same harness and metrics; `lcp` = largest-contentful-paint after the trigger (−1 = none reported within 2 s).

| lane | first ms | dropped | script ms | task ms | lcp ms |
| --- | --- | --- | --- | --- | --- |
| css (Motion.li entrance) | 38.5 | 9 | 2.4 | 569.2 | −1 |
| js (mini `animate` × 1000) | 40.6 | 6 | 9.4 | 614.0 | 660 |

- n = 1 (smoke run), same parking note.
- Reading: the CSS path scripts 4× less and reaches the first frame about as fast; both drop frames on 1000 simultaneous animations at 4× CPU (compositor-bound list). LCP: Chromium reported no LCP entry for the CSS-entrance list within 2 s (opacity 0 start), while the JS lane reported one at 660 ms. This matches the spec §10 risk. The D9 LCP rule (transform / clip only, never opacity 0 on LCP candidates) stays required for above-the-fold content; T14 measures it on a page-load LCP scenario.

## Motion suite: rivet vs motion/react vs vanilla (T14)

- Suite: `apps/dom-bench/motion/` (`build.ts`, `run.ts`, `ssr.ts`; lanes `rivet.tsx`, `react.jsx`, `vanilla.ts`). It lives in dom-bench, not a new `apps/motion-bench` workspace: dom-bench already pins React 19.3.0 + `framer-motion` 14.1.0 (the `motion/react` engine) and owns the Playwright / bench-lock helpers, so no new lockfile.

### Verdicts vs motion/react

| metric | verdict | note |
| --- | --- | --- |
| mount-1000 script / first frame / heap | WIN | 2.6× less script, first frame 2.3× sooner, heap 9.5× less |
| stagger-1000 start | WIN | 67× less script to start (React lane: 4 s of script for 1000 staggered children at 4× CPU); rivet drops more frames (4 vs 1, n = 1) while its 1000 CSS animations start together |
| relayout grid (`animateLayout` vs `layout`) | WIN | 5× less script, first frame 1.5× sooner; rivet's grid lane reads every box like Motion (2,003) and drops more frames (12 vs 2, n = 1: follow-up); masonry lanes (pure geometry, 2 reads) beat both |
| SSR 1000 Motion elements | LOSE | 2.9× slower than `motion/react` + `renderToString` (static), 2.9× (entrance); 36× the plain-`<li>` floor (spec §6 budget: ≤ 1.3×). Profile: 33% runtime `admit` (WeakSet / WeakMap + thenable probe per function-valued slot: the element `ref` and gesture handler slots), `ref()` 5%, spread 4%, style 3%. Static markup: rivet writes `opacity:1` inline (React omits it without `initial`) |
| bytes | WIN | lane bundle 1.9× smaller (br) |
| hover-first / entrance-resume | not run | React lanes need an SSR + hydration page harness; rivet side measured in `libs/motion/tests/resume.test.ts` (no boot for static / entrance / gesture pages; first hover with preloaded chunks starts synchronously) |
