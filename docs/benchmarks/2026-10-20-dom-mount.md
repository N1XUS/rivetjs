# DOM mount vs Solid (lane DOM-MOUNT, 2026-10-20)

Scoreboard 2026-10-19: `dom 1000 mount` Rivet 21.4 vs Solid 1.9 17.7 ms, `dom 5000 mount` 105.0 vs 98.3 / 84.6 (Solid 2 rc) = LOSE. Question: per-field mount cost, or something else? Base `3a0d09da`, Chromium (Playwright) cross-origin isolated, host shared with a Docker SSR lane (load 3–30, noted per run). Raw numbers: [`2026-10-20-dom-mount.json`](2026-10-20-dom-mount.json).

## Result

- **1000 rows: no gap when measured interleaved.** Stored Solid numbers date from 2026-10-06 (quieter host); interleaved today Rivet ≈ Solid 1.9 (±3 %, ranges overlap) on every run.
- **5000 rows: gap real under the run.ts protocol (−7 to −10 % vs Solid 1.9), but it is a V8 GC-scheduling artefact, not per-field cost.** Without the forced GC before the timed mount, or with incremental marking off, Rivet wins 5000 mount by 5–15 %.
- **No runtime / compiler change shipped**: every candidate either measured neutral or traded update / heap wins for mount. Tooling shipped: `build.ts --base / --lane / --emit`, `mount-quick.ts`.

## Root cause of the 5000-row loss: incremental-marking finalization delay

- run.ts protocol: warm mount + dispose → `HeapProfiler.collectGarbage` → timed mount. The forced GC leaves a ~1.3 MiB heap, so V8 starts incremental marking ≈ 11 ms into the 5000-row mount.
- When marking completes, V8 may postpone finalization to a task ("via stack guard") for up to 50 ms if its running *average time to task* ≤ 50 ms. Inside one long mount task that task never runs, so marking (write barriers, black allocation) stays on for the whole overshoot.
- `--trace-incremental-marking`, timed mount: Rivet `Completion: Delaying GC via stack guard, avg time to task: 42.1ms … allowed overshoot: 50.0ms`; Solid `Not delaying GC via stack guard, avg time to task: 53.3ms`. The average depends on the page's earlier task history, not on mount code.

## Protocol recommendation (not applied — needs a full competitor re-store)

- The forced GC right before the timed mount puts all lanes at V8's finalization heuristic, whose outcome flips on task history. Options: (a) time mount without the preceding forced GC (heap baseline taken before the warm-up instead), (b) yield one task (`setTimeout 0`) between GC and mount, (c) report the median of mounts with and without GC. Any change re-measures every competitor lane (`competitors.json` provenance rule) — orchestrator's call.

## Protocol applied (lane DOM-MOUNT-2, 2026-10-21)

- Option (b) alone does not work: `mount-quick.ts --gc-trace` (V8 `--trace-incremental-marking`, renderer stdout to a file) shows the average marking-task delay moves only when a marking task runs, so one yielded macrotask after the forced GC leaves the decision unchanged.
- Applied: warm-up mount + dispose → forced GC (heap baseline, unchanged) → **one unforced mount + dispose cycle** (heap limits grow back) → settle → one macrotask → timed mount. Protocol id `rewarm-2026-10-21` in `run.ts` results (`methodology.protocol`) and `competitors.json` `dom.provenance.protocol`; `scoreboard.ts` refuses a mount comparison across protocol ids.
