# Server segments render (lane ZERO SEGMENTS, 2026-10-26)

Follow-up of lane NATIVE (`2026-10-26-native-slice.md` in lane NATIVE's patch): get the native slice's win in JS — byte
segments + typed holes, pooled body buffers, one data walk, a cheaper router document floor. Base main `ddc0ad10c`
(includes NATIVE's per-field tail stringify).

**Verdict: two runtime wins landed, target missed.** Request CPU −10–18 % at ≥ 1000 rows (−4 % at 100 rows), output
byte-identical. The ≥ 1.5× target is not reachable without changing what the page ships: what is left at 1000 rows is
mostly bytes moving (row emitter, slab copy, socket) and the route data JSON in the tail.

## Changes

- **One `isData` walk per request.** `_rData` keeps its checked payload, its object members and their object elements
  (the router's `d`: one loader result each) in `ctx.verified`. `_rB` (`propsData`) does not walk a props member found
  there, so the page component's `{ data }` is not walked a second time. `isData` checks primitive members inline:
  50 → 28 µs per walk at 1000 rows × 11 numbers. The global `verified` (valid for the next `_rB` only) is gone.
- **One native UTF-8 write per row-emitter chunk.** `_listRows` joins a chunk's string slots into one pending JS string and
  encodes it with one `Buffer#utf8Write` call before `emit`. Per-slot calls on fresh cons strings cost ~35 ns each, mostly
  flattening: 2000 slots go from 68 to 19 µs. A slot ending in a lone high surrogate is written at once, so it never pairs
  with the next slot's low half. Room checks now bound the output by 6 B per UTF-16 unit, an exact worst case: only
  ASCII is escaped (≤ 6 B) and a non-ASCII unit is ≤ 3 B. ASCII chunks are the same as before. Non-ASCII rows now fit in
  larger chunks; before, they were bounded at 18 B per unit.

## The four goals

1. **Byte segments + typed holes from the compiler: already there.**
   - Compiled server output is frozen fragment arrays, pre-encoded once per plan (`planBytes`) and written into pooled
     slabs.
   - Keyed list rows are a tape written by a compiled row function. The WebAssembly SIMD emitter interleaves the
     pre-encoded fragments with typed holes: text / attribute escapes and int32 digits.
   - A hand-lowered whole-page twin (NATIVE `jsTwinStr`) renders 1000 rows in ~390 µs in-process. Ours takes ~780 µs.
   - That gap is not segment writing. It is:
     - the route data JSON (70 µs, also in the twin);
     - the tape + row loop (~90 µs JS + ~50 µs wasm);
     - `admit`'s tape walk (~25 µs);
     - the router render pipeline: layouts, `App`, `Router`, boundaries.
   - No new compiler target.
2. **Pooled response buffers + direct body: already on main.**
   - The router `BodyWriter` hands out views of pooled slabs.
   - The node adapter takes `DIRECT_BODY` and writes those views with one corked `writev`. No `new Response(Uint8Array)`
     copy, no fresh 800 KB buffer.
   - NATIVE's finding was about its native renderer's own output buffer.
3. **Route data walked twice → once: done** (above).
4. **Router document floor: measured, no cut.**
   - HTTP, host: a 0-row `/resume` takes 92 µs/req and the `/trivial` endpoint 38 µs, so the floor is ~54 µs.
   - In-process it is 30–40 µs, spread over the render pipeline.
   - Largest single items:
     - six `new URL` parses per request (~3 µs; defensive copies of a mutable URL);
     - `Request` + `Headers` construction (~4 µs with browser headers; the endpoint pays it too);
     - the page module's dynamic `import()` (~1 µs);
     - `admit` (~2 µs);
     - tail encode (~1.5 µs).
   - None is ≥ 10 % of the floor.

## Where 1000 rows go now (HTTP profile, busy time ≈ 100 %)

| item | share | note |
|---|--:|---|
| socket `writev` | ~12 % | 812 KB to the kernel; Razor pays it too |
| tail JSON (`encodeTail`) | ~12 % | `JSON.stringify` of the 80 KB route data (fast path) + script escaping |
| wasm row emitter | ~10–15 % | fragments + escapes + digits for 812 KB |
| `_listRows` JS | ~12 % | the slot loop, incl. flattening the per-row `href` cons strings |
| `isData`, `admit`, tape fill, `derivedRows`, GC | ~3 % each | |

- 1.5× means cutting ~1/3 of request CPU. Socket, emitter, slab copy and data JSON alone are ~40 % and cannot shrink in JS.
- The remaining levers change what ships, not how it is written:
  - **Route data read back from the DOM instead of the tail.** BE-STATE scope: the row values are already in the HTML.
  - **Typed row holes the compiler proves primitive.** This would drop the tape and `admit`'s walk, ≤ ~60 µs at
    1000 rows, and needs a Rust change.
  - **Emitter output straight into body slabs.** Slabs would have to live in wasm memory, coupling router and runtime;
    saves ~15 µs.
