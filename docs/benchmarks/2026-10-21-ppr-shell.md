# Shell cache (PPR) on the editorial article page

Lane PPR-T57 (spec `docs/design/specs/2026-10-20-ppr-shell-design.md`, T5). Hand-written; raw loadgen samples in `2026-10-21-ppr-shell.json`. Host: shared macOS dev machine (other lanes + a .NET compiler running), load average noted beside every table. Numbers are for ranking the lanes against each other, not absolute capacity.

## Page and lanes

Page: `apps/editorial-bench/spikes/ppr-shell/app`, article `story-00018` of the n1000 fixture, signed in (`sid` cookie on every request). The article body, header, nav and footer are the shell; the per-user bar (session read in a loader) is the hole (`<Async>`).

| lane | what the server does |
| --- | --- |
| `full` | today's render: the whole page per request, no shell cache |
| `shell` | shell cache hit with H-holes (default): no shell render, only the retained `Async` boundaries re-run; every 64th hit replays in full (VERIFY) |
| `shell-h` | shell cache hit with H-replay (`RIVET_SHELL_HOLES=0`): muted replay of the shell, holes streamed |
| `floor` | the same app answering `/floor/` (router pipeline + a tiny page): lower bound for any request |
| `deferred` | in-process only: the page with the hole deferred but no shell cache (cost of the deferral itself) |

## In-process (no HTTP)

Command: `node apps/editorial-bench/spikes/ppr-shell/bench.ts --pages editorial --lanes full,shell,shell-h,floor,deferred --rounds 5 --requests 1500` (web-standard handler, request → body drained). Load 5.09–5.99. Median of 5 rounds.

| --- | ---: | ---: | ---: | ---: |
| full | 0.2653 | 0.2107 | 0.1978 | 12,514 |
| floor | 0.0869 | 0.0491 | 0.0441 | 6,040 |
| shell | 0.0516 | 0.0370 | 0.0101 | 14,688 |
| deferred | 0.2877 | 0.2281 | 0.2083 | 14,436 |

`shell` = 5.1× less CPU than `full` (bar ≥ 2×); TTFB 0.010 ms vs `floor` 0.044 (bar ≤ `floor` + 0.05). In process the hit is cheaper than `floor` because `floor` renders its route; over HTTP the socket + adapter cost (~0.07 ms/req) hides the difference. (The bench's `estimates` line prints NaN when the T0 estimate lanes are not selected; ignore it.)

## Where a hit's time goes (from PPR-T6, `--cpu-prof`)

| part | ms/hit |
| --- | ---: |
| router pipeline (match, guards, `parseCookies`, `headers()`, CSP) | ≈ 0.010 |
| holes render + segment stream + patch encode | ≈ 0.008 |
| shell cache `hit` / `begin` / `answer` / body pull (prefix copy with the live nonce, `$rvh`, holes script) | ≈ 0.006 |
| WHATWG Request / Response / web streams | ≈ 0.006 |
| GC | ≈ 0.004 |
| harness read loop | ≈ 0.008 |

`deferred` − `full` (the price of deferring the hole without a cache, ≈ 0.02 ms): segment patch encode pass ~6 µs, `Stream.run` / admit ~3 µs, hole binding ~2.5 µs, deferred handle ~1 µs, GC the rest. A route that defers a hole but is never a hit pays this.

## Which pages gain

- Win per request ≈ the shell's share of (loader I/O + render CPU). The hit skips the shell's loaders and render; it still pays the router pipeline, the holes and the stream (≈ `floor` + holes).
- Big win: content pages (articles, docs, product pages, marketing) where the per-user part is small (session bar, cart badge, recommendations) and the rest is the same for everyone. Here: 3.7× req/s.
- Small win: pages whose shell is cheap (a few elements) — `full` is already near `floor`.
- No win: data grids, dashboards, search results — the expensive part depends on the request (query, user, filters), so it is the hole or the page is not eligible. Put those behind `Async` only for streaming, not for the cache.
- Replay-only entries (`SHELL-HIT-REPLAY`: H-holes off, e.g. a hole writes a signal an ancestor provides through context, see `headers-and-caching.md`) keep about half the win (`shell-h`: 1.7×).
