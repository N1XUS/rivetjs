## Method and scope

Resume browser: `156.0.8078.48`; versions: rivet `0.1.0-alpha.1`, qwik `2.0.0-rc.0`, qwik-stable `1.20.1`, solid `2.0.0-rc.13`, solid-stable `1.9.15`. Historical resume is Chrome 155, published krausest is Chrome 154; cross-major timing rankings are refused. DOM uses bundled Chromium `153.0.8010.12`, matching the committed DOM reference. Fresh competitors are compared only within the same run, scenario, and browser.

Resume: all five supported production lanes, fast and Slow 4G + 4× CPU, three fresh contexts per lane/scenario; lane order randomized per repeat, traces and precise coverage enabled symmetrically. Primary latency is input to paint; first matching mutation is secondary. The extra scoreboard resume invocation uses its stock no-trace/no-coverage protocol, five repeats, and is reported separately. Bytes are CDP encoded transfer bytes including response overhead; inline script characters are separate and not summed as compressed bytes. Prefetched JS is not synonymous with executed JS. `load` observes a 3-second idle window.

DOM: three repeats, five update samples per trial, the stock `rewarm-2026-10-21` mount protocol. Local fresh Rivet/Solid 1/Solid 2/React lanes cover 100 and 1,000 rows; 5,000 was attempted for Rivet twice (full scoreboard and fresh-process retry) and the RSS guard stopped both before a completed trial; no 5,000-row timing is reported. React 5,000 was not attempted because its documented tree exceeds the cap. Svelte is present only as a stored published krausest reference; no local Svelte or React resume lane exists. Krausest local lanes are Rivet and vanilla, not freshly built competitors. Rendering cost uses three interleaved samples per lane at each CPU rate, all nine keyed-table operations; krausest CPU keeps its three requested iterations plus stock additional runs, memory n = 3 and startup n = 5; the launcher retains individual samples which the stock renderer normally discards.

The 1,000-row resume fixture and 100/1,000/5,000-row DOM fixtures exercise large interactive pages. These benches do not contain a standalone one-button resume lane, so this run cannot establish one-button overhead or validate PRESS-LITE, picker/ListBox/Table virtualization, Async, or every changed component individually. Rendering scope here is keyed-table cost, not a rebuilt UI/docs site. No SSR bench, Docker, installs, publishing, or user ports were used.

All browser commands ran serially with `nice -n 10`. The untracked Node preload redirects ephemeral listeners into 4450–4459, logs `/usr/bin/uptime` at each trial boundary (startup: between its first-paint and throttled subpasses), and preserves renderer samples. It does not change framework code, fixture behavior, measured windows, or browser throttles. A process-tree RSS watchdog samples every 250 ms and terminates at 2,800 MiB; this is sampled RSS, not a guarantee against sub-sample spikes. Host work continued; no idle wait was used. Min–max is the reported spread, not a confidence interval. Overlapping timing ranges are treated as ties.

## Top three measured losses and proposed fixes

Ranked by Rivet/best-peer median ratio among **fresh same-browser primary input-to-paint and shipped-byte measurements with non-overlapping ranges**; correlated byte/request metrics are one loss family. Published competitors are excluded from this ranking. Secondary mutation latency is diagnostic, not a replacement for paint. Fast keyboard paint has a larger median ratio (9.6/3.7 = 2.59×), but overlapping ranges (9.2–12.7 vs 3.6–14.8 ms) make it a tie; slow navigation also overlaps (64.2–65.9 vs 41.6–74.6 ms). Proposed wins below are engineering targets, **not measured improvements**; nothing is implemented.

### 1. Pre-input JS transfer: 3.75× Solid 1

1. **Loss:** Rivet 31,168 B (31,168–31,168) vs Solid 1 8,308 B (8,308–8,308), +22,860 B; six requests vs one, slow click n = 3 (same bytes in the other conditions).
2. **Where:** `derived-runtime` transfers 14,356 B and `dom-derived-abi` 9,047 B: together 75.1% of Rivet’s JS; page 4,770 B, DOM-data reader 1,578 B, root 928 B, detail 489 B account for the rest.
3. **Profile evidence:** CDP response sizes + precise coverage identify those chunks; the 489 B detail is unused in the counter interaction, but both large chunks execute used functions, so deleting “unused prefetch” alone cannot close the gap (raw Brotli payloads 14,134 / 8,825 B, excluding HTTP overhead).
4. **Proposed fix:** use page capability proofs to separate optional derived-runtime machinery and co-load the proven common definitions/ABI closure, preserving every fallback and lazy boundary; do not replace the fixture or remove semantics to improve bytes.
5. **Expected win:** investigate a 2–4 KiB transfer reduction (about 7–13%) plus fewer requests; this is a hypothesis bounded by the 23.4 KB core/ABI transfer, not a promise of Solid parity, and must be rechecked on small and large pages.

### 2. Hovered first mouse click to paint: 1.69× Qwik 2 RC

1. **Loss:** slow `hoverClick` Rivet 34.4 ms (34.1–34.9) vs Qwik 2 RC 20.4 ms (20.3–22.3), +14.0 ms, n = 3; fast hover is not a corresponding loss.
2. **Where:** Rivet’s actual click dispatch is only 1.10 ms median vs Qwik’s 0.93 ms; the first following animation-frame callback is 26.09 vs 14.65 ms after click, placing most of the gap in task/frame scheduling.
3. **Profile evidence:** the original three traces show this gap; Rivet r0 posts its flush to a later callback around +13.1 ms and rAF runs at +26.9 ms, while Qwik’s rAF is +14.7 ms; CPU profiles show short dispatch/flush work, with driver `InjectedScript` samples kept separate.
4. **Proposed fix:** test a higher-priority posted flush task against the current `MessageChannel` in `libs/reactivity/index.ts` `hold/release`, keeping synchronous handler/default-prevention behavior and the first-mouse-click deferral contract; do not simply make all clicks synchronous.
5. **Expected win:** target 8–14 ms on this hovered slow path if the extra frame boundary can be avoided; unproven until an interleaved mouse/keyboard/touch and headed/headless check shows no regression in the cold non-hover case.

### 3. First filter key to paint: 1.59× Solid 1

1. **Loss:** slow `filterKey` Rivet 69.2 ms (65.6–71.3) vs Solid 1 43.6 ms (42.7–44.9), +25.6 ms; mutation latency is 32.3 vs 12.1 ms, n = 3.
2. **Where:** original trace `input` dispatch medians are 29.47 vs 9.50 ms; profiling points to node reconciliation, deferred DOM-data reads and the lazy current-node snapshot, beyond the necessary 900 row removals.
3. **Profile evidence:** diagnostic n = 3 self-time medians: Rivet `removeChild` 5.38 ms vs Solid `remove` 4.90 ms; Rivet `reconcile` (`vn`) 4.56 ms, DOM-data reader module 4.29 ms and derived runtime 5.09 ms; the observed Proxy `get` maps to `lazyNodes`, while `c` maps to `domText`.
4. **Proposed fix:** unwrap the frozen `lazyNodes` snapshot once at the reconciliation boundary instead of repeated Proxy array access, and avoid repeated DOM-backed value work during that same pass; preserve the snapshot-before-mutation rule and lazy-row ownership/adoption behavior.
5. **Expected win:** target 3–8 ms less first-input task work (roughly 9–25% of mutation latency); paint may save zero or one frame depending on phase, so a 25.6 ms paint improvement is not claimed without a same-host A/B.

Profile caveat: the separate CDP CPU sampler uses 100 µs sampling at 4× CPU and includes Playwright calls and predicate polling. Its absolute time is not the headline runner latency, and per-module self medians are not additive.
