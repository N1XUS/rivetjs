# Docker SSR comparison with React — 2026-10-27

Generated by `apps/ssr-bench/fair-report.ts` from the runs listed under Inputs. Every number below is a median over ≥3 interleaved repeats with the trial range as subscript (min–max).

## Methodology

- **SSR** (`apps/ssr-bench`, Docker): every lane 1 CPU / 512 MiB, same gRPC backend (2 CPU), same DTO, strict validation of every row/field (sampled strictly every 32nd response + length checks). Node load generator `loadgen/` v2 (sha `feca615ea273`), 10 s measured after 3 s warmup per trial, 3 repeats with rotating lane order, 10 s unrecorded prewarm per lane (JIT tiering). Closed loop c=1/10/100.
- **GC profiles (B2)**: identical for every Node lane. `tuned` = `--single-threaded-gc --max-semi-space-size=8` (Razor: `DOTNET_gcConcurrent=0 DOTNET_GCgen0size=0x1000000`); `default` = runtime defaults for everyone. Container commands are recorded per run (results.json metadata.provenance.commands).
- **Like-for-like classes (B3/RA3)**: *static* — `rivet-compiled` (Rivet compiled JSX, no resume data) vs Razor, Solid 1 compiled `hydratable:false` + `renderToString` and React 19 `renderToPipeableStream` (no bootstrap); *resumable/hydratable* — `rivet-resume` (`/resume`: file route + nested layout with state, keyed `<For>`, per-row click handler + reactive attribute + `<Link>`, resume state) vs Solid 1/2 (`hydratable:true`, hydration keys), React 19 interactive (same per-row work, page data as hydration JSON + bootstrap script) and Qwik 1/2 (container state). Peers render the same page without handlers, so the resumable comparison is conservative for Rivet. `rivet-router` (router + resume render, no handlers) and `rivet-for` are shown for attribution.
- **Verdicts (B4)**: WIN/LOSE only for a ≥3% median gap with non-overlapping trial ranges; else TIE (`apps/dom-bench/verdict.ts`).
- **Escaping (B5)**: `--strings` variant — every field is text, field 3 of each row (10%) is `<b>"N"</b> & 'é€漢字𝄞'`; the validator compares exact characters after HTML parsing (any valid escaping accepted, raw markup rejected).
- **HTML bytes**: mean successful response body bytes (chunked framing excluded).
- Machine: 8 input file(s); host see results.json metadata.

## How this run was made (lane BENCH-REACT)

- Source: `main` at `a277d2ab3` plus the React lanes of this change. One Node lane image (`rivet-ssr-bench-node:benchreact`, `af91b4093fa6`, Node 26.11.1) holds every Node lane's bundle; the backend (`56a3c4a633d6`), Razor (`383b48eaa048`) and the load generator (`rivet-ssr-bench-load:v2`, sources sha `feca615ea273`) images are the ones the 2026-10-23 run used. The provenance (generator sha, 10 s window, 3 s warmup, 3 repeats, 10 s prewarm, tuned GC) matches the 2026-10-23 report.
- New lanes: `react-static` (React 19.3.0 `react-dom/server` `renderToPipeableStream`, static page, no bootstrap: static class) and `react-interactive` (the same per-row handler, state-driven `data-state`, links and nested layout with state as `solid-stable-interactive`; page data as hydration JSON in `bootstrapScriptContent`, plus the client script tag: resumable/hydratable class). Both resolve React through `apps/bench-stable` and use the same gRPC data client, validation, quotas, image and GC profile as every Node lane. The React response streams through the same `NodeStreamWriter` as the Solid lanes. An in-process check (1000 rows, 5 interleaved rounds × 100 renders) showed no measurable cost for that wrapper against piping straight into a Writable: 9.7–11.5 ms with the wrapper, 9.7–10.9 ms without it. React's own render of the 1000-row page takes about 10 ms on the host.
- Matrix: 12 lanes; integer pages at 100 / 1,000 / 5,000 rows (concurrency 1) and 100 / 1,000 rows (concurrency 10), plus the text grid (`--grid`) and the escaping variant (`--strings`) at 1,000 rows, concurrency 1. That makes seven batches, each prewarmed for 10 s at its own row count, as on 2026-10-23. There were 252 recorded trials, with zero failed responses, zero validation errors and zero generator warnings.
- **Host load**: three other agent lanes were running builds and tests on the host throughout, and the run did not wait for the load to drop. The 1-minute load average sampled at every trial boundary was 4.1–59.1, median 8.3. Per batch (min / median / max): c1-r100 4.1 / 9.1 / 16.6; c1-r1000 4.7 / 9.8 / 22.4; c1-r5000 6.2 / 12.1 / 23.8; c10-r100 5.0 / 7.0 / 21.8; c10-r1000 6.1 / 8.4 / 27.3; grid 5.5 / 6.7 / 59.1; strings 4.9 / 9.3 / 43.3. Every trial records its load (`results.json` `cases[].host_load_1m`). The 2026-10-23 run saw 4–7. Trial ranges are therefore wider, and more pairs are TIE under the ≥3% + non-overlapping-ranges rule. Single noisy trials show up as wide subscript ranges, for example Razor at 1,000 rows c10.
- **Docker on macOS**: Docker Desktop 29.1.2 runs a Linux ARM64 VM (10 vCPUs, 16 GiB) on an Apple M4 Pro (14 cores). Each frontend gets 1 CPU / 512 MiB inside that VM. Syscall and network costs are higher than on bare Linux.
- **DOM** (`apps/dom-bench/run.ts`): rivet / solid / solid-stable / react, 3 rounds × `--repeats 3 --samples 5`, lanes interleaved, mount protocol `rewarm-2026-10-21`, Playwright Chromium 153.0.8010.12, cross-origin isolated. ## Rivet vs React (this run)

- Static (rivet-compiled vs react-static), integer pages: Rivet uses about 1/8 of React's CPU per page at 100 rows (0.17 vs 1.35 ms, c1). The gap grows with page size: 0.36 vs 14.3 ms at 1,000 rows (about 40×) and 1.48 vs 91.8 ms at 5,000 rows (about 60×). Complete p50 and TTFB win in every case. Peak memory wins in 4 of 5 cases, with 1,000 rows c10 a tie. HTML bytes are a tie: React adds about 1% (`<!DOCTYPE html>`, `charSet`, self-closing tags).
- Resumable (rivet-resume vs react-interactive): Rivet wins CPU per page, p50 and TTFB in every case: 0.91 vs 18.9 ms CPU at 1,000 rows c1, and 4.10 vs 90.8 ms at 5,000 rows. Peak memory is mixed. Rivet wins at concurrency 1 (91 vs 120 MiB at 100 rows, 121 vs 142 MiB at 1,000 rows) and loses at concurrency 10 (189 vs 139 MiB at 100 rows, 171 vs 149 MiB at 1,000 rows); 5,000 rows is a tie. HTML bytes lose at 100 rows (84.2 vs 78.3 KB, +7.5%) and tie at 1,000 and 5,000 rows (+2%). Rivet ships per-row markers and the boundaries tail, while React ships plain markup plus the page JSON.
- Text grid / escaping (1,000 rows, c1): Rivet wins CPU in both classes. On the grid, static is 1.99 vs 20.2 ms and resumable 2.94 vs 20.9 ms; with escaping, static is 1.34 vs 18.4 ms and resumable 1.95 vs 19.6 ms.
- DOM: Rivet is faster than React on every measured metric at 100 and 1,000 rows. At 1,000 rows, mount takes 17.0 vs 39.7 ms, update100 2.60 vs 20.0 ms, and heap is 4.06 vs 16.8 MiB.
