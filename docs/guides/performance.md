# Performance guide

Rules for runtime / cdk / router hot paths. Every change still needs a measured win (ssr-bench, dom-bench, size-report); this page records measured idioms so lanes do not re-measure them.

## Hot path idioms

Measured by lane HOTPATH 2026-10-09 (Chromium CDP profiles of cdk mount lanes, Node 26 in-process SSR). Ratios are mount-time medians on interleaved fresh pages.

- **Memoise pure Intl work per locale string.** `new Intl.Locale(…)`, `Intl.*.supportedLocalesOf`, `resolvedOptions()`, calendar creation are µs-scale; cdk called them per component / per segment. Bounded `Map` keyed by the locale string (or `locale|option`), `WeakMap` keyed by the formatter. cdk `i18n` `isRTL` / `getDefaultLocale`, `state/date-field.ts` `resolveCalendar` / `resolvedOptionsOf`: DatePicker ×300 −19%, Select / ComboBox −14%.
- **Parse once per key string.** Per-element regex / `toLowerCase` / set tests on prop names (`onKeyDownCapture` → type, capture, delegated) belong in a module-wide cache keyed by the name, bounded (512) so arbitrary keys cannot grow it. runtime `_spread` `listenerOf`: Checkbox ×1000 −12%, TextField −8%.
- **Memoise derived arrays by identity.** A list derived from an immutable array (segment keys from `segments(state)`) → `WeakMap<source, derived>`; hand callers a `.slice()` if they may mutate.
- **No `FinalizationRegistry.register` per instance.** Registration costs more than the object it watches. Use a `WeakRef` list pruned at power-of-two lengths plus an amortised sweep when the map doubles (cdk `utils/id.ts`).
- **Keep `JSON.stringify` input on V8's fast path.** Node 26's fast serializer bails for the WHOLE call (~3×) on one sliced or cons string, or one object with integer / digit-leading keys. Flatten strings you slice yourself with an own-key round trip (`Object.keys({ [s]: 0 })[0]`, ~0.1 µs; `.trim()` / `Number()` flatten cons strings, not sliced ones); write integer-keyed maps by hand and stringify the rest in runs (runtime `resume-format.ts` `flat`, `server-resume.ts` `idMap` / `bindingsJSON`: 100-row resume table 26 → 7.8 µs, bindings 4.0 → 1.6 µs; derived tail `server-tail.ts` `encodeTail` stringifies per top-level field because `c` / `k` are integer-keyed: 81 KB tail of `/resume` 1000 rows 385 → 68 µs). Escape scans: `indexOf` + `replaceAll` with a one-character pattern (memchr) over a regex (10 KB 2.5 → 0.2 µs).
- **Delegate hover / focus; no native listener per element.** React semantics without per-element listeners: delegated `pointerover` whose `relatedTarget` is outside `currentTarget` = pointerenter (`hoverStateOver`); delegated `focusin` with `target === currentTarget` = focus, plus one transient native `blur` listener while focused (`focusStateIn`). Bind the user's `onPointerEnter` / `onPointerLeave` only when given (`onX={user ? (e) => user(e) : undefined}` binds nothing when unset). cdk Table ×1000: listeners 28k → 8k, mount −8%, dispose −20%, heap −7%; DatePicker ×300: listeners 7500 → 300, dispose −19%, heap −6%.
- **Frozen arrays iterate slower, cached encodes do not care.** `Object.freeze`d arrays iterate ~3 ns/element slower on Node 26, but SSR writers iterate cached `encoded()` `Uint8Array[]` (plain arrays); un-freezing the SSR constants measured within noise. Do not freeze per-call literals carrying accessors (see `libs/runtime/CLAUDE.md` server notes); frozen module constants are fine.
- **`style.cssText`, not `setAttribute("style")`.** The attribute write is faster in a micro but CSP `style-src` without `'unsafe-inline'` blocks it; CSSOM writes are allowed.
- **Insert with an `insertBefore` loop.** Faster than building a `DocumentFragment` or `append(...nodes)` for the row / child counts we render.
- **Descriptor scans cost ~21 ns per key.** `Object.getOwnPropertyDescriptor` in a loop and `__lookupGetter__` cost the same on V8; skip the scan (flag at creation) instead of swapping the API.
- **One pass, not `map` + `filter`.** Chained array helpers allocate an intermediate per call; a single loop pushing into one array is the hot-path form.

Measured by lane CODE-SMELL-A 2026-10-11 (Node 26 in-process micro-benchmarks, interleaved, median; numbers in the commit bodies).

- **Bounded caches apply to every per-key / per-header parse.** cdk `globalDOMProps` / `textInputDOMProps` (key → regex match, 512): `pick` over a 12-key part bag −41%; router node adapter `negotiate` (Accept-Encoding string → encoding, 64): 307 → 6 ns. Keys / headers are user / client text: always cap the Map.
- **Constant array literal arguments are free.** `hasLiveProp(props, ["class"])` vs a hoisted constant: same ns and bytes (TurboFan escape analysis drops the literal once the callee inlines). Do not hoist them for speed.
- **Create rarely used per-element side tables on first use.** DOM `_spread` state: 4 of its 5 empty objects (`own` / `direct` / `handlers` / `names`) are needed only for direct listeners or past the name cap; `??=` at the use site: 364 → 190 B per spread element.
- **Compact in place instead of `filter` per step.** `_class` toggles: one array per call (split, trim the empty ends, in-place removal): 1 base + 2 toggles 159 → 115 ns, 1.18 → 0.59 KB.
- **Pass the match you already have.** A memoised matcher still costs a call + result object per lookup: router `_layouts` passing its hit to `keysOf` −7% per SSR request.
- **Getter scans: keep the per-key descriptor loop.** Over an 8-key static bag `Object.getOwnPropertyDescriptors` is 5.4× slower and `__lookupGetter__` +39% (alloc-free, still slower); `for…in` is only −5% and walks inherited keys / proxy traps — not worth the semantic change (CODE-SMELL-B).
- **Allocate result lists on first need.** `mergeRefs` building its cleanup list only once a ref returns one: 16.0 → 10.8 ns, 185 → 1 B per call; `liveOptions` indexing `keys` then `controlled` instead of joining them: −15%, −231 B per part.
- **Short exclusion lists: `includes`, not a `Set`.** A 3-key `liveOmit` with a fresh `Set` is +24% (the Set costs more than the scans it saves).

Measured by lane RESUME-DROP-MARKERS 2026-10-18 (Chromium 141 CPU profiles of the resume-bench `filter` keystroke, 4× CPU; numbers in `apps/resume-bench/CLAUDE.md`).

- **Large-DOM mount: per-field cost is not where Solid wins.** Lane DOM-MOUNT 2026-10-20 (CPU profiles, 5000 rows × 10 fields): Rivet 2048 vs Solid 1.9 2145 ns / field; the run.ts 5000-row LOSE is V8's incremental-marking finalization delay after the forced GC (`docs/benchmarks/2026-10-20-dom-mount.md`). Keep the `_tx` placeholder `Text`: element `_t` / `firstChild` text bindings mount 3–4 % faster but update100 +20–53 %, update1 +30–38 %. Whole binding layer ≤ 4 % of mount (static-text lower bound). Shape pins that pre-take disposal's first field writes (`disposed`, `fn`, `sources`) remove V8 constness deopts at the first unmount yet measure neutral (run.ts, krausest 01 / 07 / 08) — not worth bytes. Lane DOM-MOUNT-2 2026-10-21 (`docs/benchmarks/2026-10-21-dom-mount-2.md`): run.ts now re-warms once after the baseline GC (protocol `rewarm-2026-10-21`, no marking cycle inside the timed mount); re-stored competitors → mount 1000 / 5000 TIE with Solid 1.9 / 2 rc, every update / heap row WIN. Allocation is not the lever: Rivet allocates 5.4 KB / row vs Solid 1.9 8.8 / Solid 2 10.7 KB (CDP sampling incl. collected objects); runtime-owned records are ≈ 190 of 545 B / field (ArgNode 96, signal 84); +20 B / field (+3.7 % bytes, padded ArgNode) moves mount within noise (+1.4 % / −2.2 %). A signal getter inheriting `set` / `update` from a custom prototype (no property array) makes `bind` take V8's slow path: 42 vs 11 ns per signal — keep own properties.
Measured by lanes LAZY-COST / LAZY-COST-2 / VIRT-LEAK 2026-10-21 (in-process story harness + Docker ssr-bench `/resume`; `docs/benchmarks/2026-10-21-lazy-cost.md`, numbers in the commit bodies).

- **No renderer per row.** One `renderToString` per lazy row (renderer, owner record, id scope, then a second copy into the page writer) cost ~4× recorded rows (GC 219 vs 50 µs / render at 1000 rows). Write row-plan rows from one list tape through the wasm emitter, and render rows that hold nothing left to run 32 per renderer (`LAZY_BATCH`): 0.33–0.75× recorded. 32-row batches beat one renderer per `For` (+10–25 % CPU) and handing row values straight to the page writer (+15–20 % on `/lazy-rows`).
- **A Node timer keeps its async context.** A `setTimeout` created during a server render holds the `AsyncLocalStorage` frame it was created in — the render's whole recorder — until the timer phase, which in-process loops never reach and a busy server reaches late (cdk `/virtualized-collections` 12 MB retained per render). Create deferred work from a context snapshot taken outside the render (`store.exit(() => AsyncLocalStorage.snapshot())` at module load; reactivity `_scheduleFolds`): 0.2 MB / render, CPU −14 %. Any timer or pending promise a render schedules pins it the same way.

- **Every `removeChild` costs; a comment's about a third of an element's.** Removing 1,800 marker comments next to 900 `<li>`s was +16 ms on a 46 ms removal pass (4×). A `Range.deleteContents` per contiguous run saves nothing (Blink removes node by node inside it); only a whole-parent wipe (`textContent = ""` / `replaceChildren`) is bulk, and it re-inserts what is kept (focus / media / animation state lost), so it stays limited to the nothing-kept path. Leave inert markers in place instead of removing them one by one (`dom-adopt.ts` `left`).


Measured by lane ZERO BE-RENDER 2026-10-25 (Node 26 in-process: `frames-cpu` over the ui-docs production server, interleaved; heap sampling profiles).

- **`Object.keys`, not `Reflect.ownKeys`, for own enumerable keys.** `Reflect.ownKeys` builds a fresh key list every call (~90 ns, ~390 B for a 3-key props object); `Object.keys` takes V8's enum cache (~12 ns, ~70 B), + `Object.getOwnPropertySymbols` filtered by `propertyIsEnumerable` for the same order and symbols. runtime `splitProps` / `_restProps`: 195 → 166 ns, 873 → 559 B per live split; table-virtualization (1000 rows) 17.6 → 16.3 MB alloc / request.
- **Discarded passes open no boundaries.** A cdk collection build pass (`_rUnrecorded`) evaluates every row's parts to register nodes; on the server each part's `_rB` made a boundary, a context frame (and its lookup memo `Map`) and often a record the page never used (ui-docs: 3,864 of 11,467 tail records, no markers). `_rB` returns null inside such a pass: table-virtualization 16.3 → 13.6 MB alloc, wall −21 %.
- **Memoise accessor results that rebuild lists.** A props object whose `items()` / `value()` / `onChange` each rebuilt a 20-entry formatted list (`calendarYearPickerProps`) did the `Intl` work four times per render; key the last result on the inputs read (they are still read on every call, so tracking is unchanged).

Measured by lane ZERO SEGMENTS 2026-10-26 (ssr-bench `/resume` page through the real node adapter, Docker Linux Node 26.11.1, gRPC data, interleaved lanes; in-process handler A/B; `docs/benchmarks/2026-10-26-segments.md`).

- **Walk data once per render.** A value checked as JSON data a moment ago is not walked again: `_rData` keeps its payload and loader results in `ctx.verified`, `_rB` (`propsData`) skips a props member found there (the page's `{ data }`). 1000 route rows: two `isData` walks → one. The one walk waits for the first flush that writes records (ROWS-SSR `settle`): a renders-only route (no tail) walks nothing (`/page` 1000 rows −130 µs in-process).
- **Inline primitive checks in recursive walkers.** Test number / string / boolean members in the loop (`v - v === 0` = finite) and recurse only into objects: `isData` over 1000 rows × 11 numbers 50 → 28 µs.
- **One native string write per chunk, not per short string.** A `Buffer#utf8Write` call on a fresh (cons) string costs ~35 ns, mostly flattening; join the strings into one pending JS string and encode it once (UTF-8 of a concatenation = the concatenated encodings). Exception: a string ending in a lone high surrogate is written at once, or the next string's low half would pair with it. Row emitter 2000 string slots 68 → 19 µs; `/resume` 1000 rows −10–18 % request CPU together with the item above.
- **Measured no gain (do not retry):** per-plan slot-kind tables instead of reading `attributes[k]` in the row loop; 64-byte unrolled fragment copies in the wasm row emitter (fragment copies are not its bottleneck); a JS ASCII loop instead of `utf8Write` for short strings (57 vs 68 µs: flattening dominates either way).

Measured by lane ZERO X7 2026-10-26 (static parts of server output; in-process handler over the docs / ui-docs production builds; `docs/benchmarks/2026-10-26-x7-static-server.md`).

- **One `Intl` formatter per option set, never `toLocaleString(locale, options)` per value.** `Number.prototype.toLocaleString` with a locale or options builds a new `Intl.NumberFormat` on every call (~10 µs): docs-kit `chart-model.ts` `formatValue` / `formatTick` were 80 % of the server render of `/about/benchmarks/` (4.3 → 0.8 ms, same bytes). Cache the formatter (`new Intl.NumberFormat(locale, options).format` is the same algorithm).
- **Static markup is already one pre-encoded segment.** Compiled server output hoists frozen fragment arrays (static elements, attributes, text and the `<!--[-->` markers between them), the runtime UTF-8-encodes each array once (`encodedFragments`), and list rows share a precomputed plan (`_listPlan`) that inlines static child components' fragments. What still costs per request is the walk over holes (record walk + `admit` + attribute / text escaping), component calls and derived recording — on a docs page ≈ 65 % of render CPU is assembling output that is the same on every request, but almost none of it is provable at compile time (it flows through live boundaries' props, cdk / ui components with contexts and spreads). Inlining static child components by hand saves ~16 % on a 100-card synthetic page; only a whole-subtree constant (prerender) reaches the ~20× ceiling.

Measured by lane BEAT-RAZOR 2026-10-26 (ssr-bench router build, Docker 1 CPU / 512 MiB, Node 26.11.1, tuned GC, C# gRPC backend, in-network driver, interleaved rounds; `--trace-gc-nvp` promoted bytes / request).

- **Send a synchronous page whole.** A page that finishes rendering before anyone reads it goes out as one corked writev with a Content-Length; streaming it chunked from its first 64 KiB (renderer queue) cost a Response hand-off mid-render, more writes and an in-flight render graph per request that scavenges promote (8.8 → 2.9 KB/req). Router `QUEUE` 64 → 256 KiB (= the node adapter's `MAX_BUFFERED`): `/resume` 100 rows c10 CPU/page 212 → 153–177 µs, p99 9.5 → 4.3–9.4 ms; `/page` 155–190 → 117–120 µs; 1000 rows (≈ 780 KB, still streamed) unchanged. Coalesce while a sink drains (`threshold` = `FLUSH_AT`, not 0: one chunk per write otherwise).
- **Hand web objects what they copy anyway.** `new Request(url, { headers })` fills and validates its own header list: building a `Headers` first validated and stored every header twice (node adapter `toRequest` now passes name / value pairs). Server `createRouter(url)` no longer reparses the request URL, and a page URL the static index lacks skips the async file lookup. Together −2–4 µs per routed document (host interleaved A/B, within noise of Docker). Measured, not landed: an own `signal` on the bridged Request instead of undici's signal-following (`new Request(url, { signal })` 2.6–3.1 µs vs 1.3 µs: its AbortController, `addAbortListener`, WeakRef and FinalizationRegistry cell) — `new Request(event.request)` / `clone()` copies would stop following the client disconnect.
- **Promoted bytes / request follow in-flight time, not the request signal.** The 8 / 18 KB-per-request "modes" of the router lane appear and vanish with host load (backend + driver latency keeps more requests in flight across scavenges); the loader without `request.signal`, or with an own signal, shows the same modes. One-shot pages cut the in-flight window: 2.6–3.9 KB/req at ordinary load.

Measured by lane SSR-130 2026-10-27 (ssr-bench `/resume` 100 rows; host Node 26 in-process loop over the router build with sampled allocation profiles, paired rounds; HTTP through the node adapter, gRPC backend, c10, 5 interleaved rounds; host load 8–20).

- **Escape and write long JSON as its own string.** The boundaries tail was one concatenation of every field's JSON; `escapeJSON`'s `indexOf` flattened the whole cons string (7.5 KB copied, ~15 KB allocated per request at 100 route rows). `tailPieces` escapes each field's `JSON.stringify` result and keeps a field ≥ 512 chars (`b`, the route data) as its own fragment of the tail record — same bytes (escaping is per character). With the two items below: 149 → 137 KB allocated per request (−8 %), scavenges per 1000 requests 27.6 → 25.4.
- **Mark small integer keys in a byte map, not a Set.** `For` / `_rFor` duplicate-key checks (`_forKeys`): keys that are non-negative integers below 4 × rows + 64 (row ids) set a `Uint8Array` byte; any other key takes the Set. Same answer (a value always lands in the same structure; `-0` = `0` as SameValueZero). 100 rows 1.4 → 0.3 µs, −5 KB per request.
- **Check primitive array members in the caller's loop.** `isData` on an object member that is an array (`values: [10 numbers]`) checks its primitive elements in place (`leafData`), recursing only at the first non-primitive: 100 rows 3.4 → 2.5 µs per walk.
- **Measured no gain (do not retry):** fused JSON validate + encode in JS (2× slower than `isData` + `JSON.stringify`, which is at V8's floor: 5.75 µs for the 100-row payload; packed vs holey arrays no difference); `for…in` vs `Object.keys` / `Object.values` in `isData`; an undici `Request` without `signal` (promoted bytes per scavenge unchanged, 511–575 vs 528–567 KB — confirms BEAT-RAZOR's finding above). Whole-request CPU deltas of these items (≈ 2–3 µs together) are below this host's paired-round noise (A/A ± 3–7 µs); the allocation profile is the deterministic measure.
- **What the 100-row tail still costs:** `JSON.stringify` + `isData` of the route data ≈ 12–13 µs of a host `/resume` request (≈ 9 µs in Docker) — the largest remaining runtime item; removing it needs the data shipped once in another form (domData default — on since DOMDATA-DEFAULT, below —, or a compiler projection of the fields the client reads), not a faster walk.

Measured by lane DOMDATA-DEFAULT 2026-10-27 (`resume.domData` on by default, user ruling; ssr-bench router-app built twice, `domData: false` vs default; host Node 26.5.1, in-process `loadBuild` handler over a host gRPC backend, paired rounds 30 × 500 requests; story harness `apps/ssr-bench/spikes/lazy-cost/client.ts`, headless Chromium, 4× CPU, n = 7; host load 6–9 for CPU, 5–20 for the browser):

- **DOMDATA-DEFAULT: ship list rows once.** `/resume` 100 rows: HTML 84,085 → 77,360 B (br 4,909 → 4,274), boundaries tail 7,572 → 845 B; 1000 rows: 813 → 733 KB (br 24.3 → 17.5 KB), tail 81 KB → 846 B. Server CPU paired Δ: 100 rows −4 … −12 µs in 4 runs (A/A of the same harness −16 µs, IQR ±30: direction only, within noise), 1000 rows −13 / −62 µs. Client cost: `/resume-1000` first row click paint 37 → 45 ms (dom 29.5 → 41.2 ms), first non-row click 43 → 48 ms; pages without a qualifying list (`/list-data`, `/dom-data`: cdk collections) within noise. `resume: { domData: false }` ships neither.
- **DOMDATA-DEFAULT v2: pay only where a list is.** Builds serve the switches only when the walk saw a keyed `<For>` with DOM slots (`domListIn`): every other app is byte-identical to `domData: false` (zero-cost `runtime.txt` unbracketed / `[resumed]` unchanged; size-report starters + kit fixture unchanged; lanes: only `rivet-router`). The browser reader is its own chunk (`dom-data-reader.ts`), fetched only by pages with `d` entries: list apps' runtime +326 B min / +139 B br (ui-docs frames), `[domData]` runtime 60,794 → 58,158 B; server +5.8 KB min (encoder). Story harness at 4× (load 18–22): `/resume-1000` row click paint 42.4 → 44.1 ms (dom 32.9 → 42.4), ctl 49.5 → 47.8, JS before input 42.7 → 44.3 KB (reader preloaded), state br 8,553 → 402 B; `/list-data` (no `d`) within noise, reader not fetched.

Measured by lane SELF-WRITE 2026-10-27 (Node 26 in-process, 2 M writes, median of 9; host load ≈ 30):

- **Untracked self-write: `x.set(x() + 1)`, not `x.update((v) => v + 1)`.** In a handler nothing is tracking, so the read returns early from `track`, while `update` allocates its closure and swaps the observer through `untrack`: 2.6 vs 5.8 ns per write when the signal has no subscribers, 44.0 vs 47.3 ns with one subscribed effect to flush. In an effect / computed the read subscribes the scope to its own write — use `update` there (RV1017, language service).

## Incremental lists (INCR2 2026-10-26, opt-in)

- `rivetRouter({ resume: { incr: true } })` + `start({ incr: createIncrCache() })`: compiler proves row purity (`libs/compiler/rust/src/compile/incr.rs`), runtime reuses row bytes per list (`libs/runtime/incr/`). Byte-identical (differential `libs/runtime/tests/server-incr.test.ts`).
- 1000-row list (block-body row + keyed row signal), in-process handler µs/req median, base → incr (host load 15–25, other lanes): 0% 722 → 137 (5.3×); 1% 793 → 192 (4.1×); 10% 794 → 317 (2.5×); 100% 841 → 857 (−1.9%: cold state + probes); shift (insert + pop per request, key realign) 675 → 380 (1.8×); grow 1 row/request 1076 → 535 (2×); fresh objects per request (`rows().map(r => ({ ...r }))`) 0% 639 → 212 (3×), 1% 682 → 296 (2.3×) (no data memo: tail JSON + isData walk per request); 10-row list 32 → 29. Process RSS +30–60 MB at 1000 rows (cache ≈ 0.23 MB per list + data memo + GC headroom).
- Remaining at 0%: harness `Response.text()`, user `each` filter, compare loop, router floor ~25 µs. Data memo (`incr/data.ts`) only for deeply frozen arrays ≥ 64 (immutable stores); positional compare — shifted arrays rebuild it.
- Lessons: frozen objects / arrays take `JSON.stringify`'s slow path; per-request WeakMaps (ephemerons) cost GC at 100% change; retaining the previous request's objects promotes garbage (cold lists keep 16 sampled items only); one `TextEncoder.encode` of concatenated ASCII rows beats per-row views.

## Incremental builds (INCR-BUILD 2026-10-29)

- Exact memos only: every cache key covers everything the result depends on, so a warm build writes the bytes a cold build writes (acceptance: ui-docs dist trees diffed; equal except files that differ between any two builds: `sidebar-skeleton` random widths, `time-field-disabled` / scheduler "today" (clock), Pagefind `pf_filter` / `pf_meta` names).
- Compiler: `wasm.ts` `setCallCache` (`rivet({ compileCache })`, default on, `<rivetCacheDir()>/compile/`: env `RIVET_CACHE_DIR`, else `<os tmpdir>/rivet-cache`): key = wasm bytes + registered tables + request JSON. Cross-module facts are request options, so no invalidation logic. Compile was a small share: −5…−10 s of a ~105 s ui-docs Vite phase.
- Router: brotli q11 sizes of `inlineStylesheets` memoized by CSS hash (`route-css.ts` `brotliSizes`): ~9 s per ui-docs client build (two client builds per docs build: co-load pass 2 hits pass 1 even cold). Route-list scans (`isRoute`, head strip) resolved once per build: ~1.5 s per client build.
- docs-kit: `tools/build-cache.ts` per-page passes — Shiki tokens per block (~6 s), critical CSS per page (~9.5 s, entry = new head + sheet hashes).
- ui-docs, 14 cores, `nice 15`, 3 runs each (before = HEAD 25b7b432e): cold (all caches wiped) 261 / 267 / 286 s → 262 / 266 / 261 s (neutral; cache writes ≈ +2 s critical); warm, one example edited (check cache warm in both) 154 / 159 / 156 s → 105 / 105 / 100 s (−34 %; Vite 120 → 84 s, prerender 13 → 7 s, critical 12 → 2 s); peak tree RSS 2.70–2.72 → 2.72–2.73 GB.
- Cache location: never inside the app. Tailwind v4 source detection scans the app dir (`node_modules/.vite` included); INCR-BUILD-01 kept the compile cache in `.vite` and its JSON added utilities (starter-ui `/` route sheet past the inline limit, htmlBr 3648 → 7345; reverted 4d6a2b04c). INCR-BUILD-03 moved the rest: comptime results (`comptime/`, were `<Vite cacheDir>/rivet-comptime/`), `?image` / `?svg` cache (`images/`, was `node_modules/.rivet/images`), docs-kit example-check cache (`docs/<app hash>/example-checks.json`, was `<app>/.artifacts/`). Kept in the project on purpose: the kit Google-font download cache (`node_modules/.rivet/fonts`: woff2 + Google CSS only, no class text; dev serves the font files from disk, so outside the root would need `server.fs.allow`; documented as the offline-CI restore path).
- Left (not exactly memoizable per module): rolldown bundling + minify, Tailwind `generate` (~3.5 s / build), comptime + class-merge parse / walk (~3.5 s / client build: results depend on other modules' tv definitions), the co-load pass (a second client build + pass-1 prerender: its plan depends on pass 1's chunk sizes and names). Prerender render itself 4.4 s (every page embeds manifest data; no per-page dependency record) and llms 1.3 s: not cached.

## First interaction (ZERO ONDEMAND 2026-10-26)

- **Fetch the handler list at once, not the import chain.** On intent the loader appends every `data-fo` URL as a high-priority modulepreload: Slow 4G + 4x CPU first click without background fetch 4.4 s → 1.1 s (button-basic), 5.0 → 1.4 s (ui-docs median), 5.4 → 2.3 s (scheduler-views), against walking the target's imports.
- **Keep the idle background fetch on.** With it the first click stays at 17–25 ms on Slow 4G (and 9–19 ms fast); without it (`ahead: "intent"`) it costs one round trip + the list (0.6–2.3 s); a 300 ms hover hides only 0.2–0.45 s of that. Default `idle`; `intent` for pages scored on bytes only.
- **Prime at idle, dispatch in the input task (LITE-BOOT 2026-10-29).** Fetched-but-unevaluated code still made the first event wait for an `import()`, which Chrome resolves only after the next frame (+1 frame, settings submit 49.6 ms vs Solid 1 34.3). With the background fetch-ahead the loader now starts the runtime and loads the listening modules (`rt.w(document)`), so the first event adopts and runs in its own task: settings fast 49.6 → 36.4 ms, ui data-grid checkbox 52.5 → 15.0 ms (Slow 4G + 4x 57.6 → 33.6), kanban 130 → 76 ms slow; cost +0..+7 ms CPU before input fast, up to +34 ms at 4x on big ui pages (idle, no long task), +26 B br loader. `docs/benchmarks/2026-10-29-lite-boot.md`. Router pages (ROUTER-PRIME): the route's page chunk is on the idle list too and the prime runs `Root.ready`, so the first press skips that import (fast 31 → 15 ms, Slow 4G + 4x 181 → 14 ms on nested-layouts) for one more low-priority request before input. `docs/benchmarks/2026-10-29-router-prime.md`.
- **Adopt on the pointer pass.** Booting on a held hover adopts the boundary before the press: holding hovers until an 80 ms rest made a no-rest click pay the adopt after pointerdown (prompt-suggestion 11 → 38 ms fast, 17 → 45 ms Slow 4G). The dwell is kept for `intent` pages only, where a pass must not fetch.
- **Page-wide behaviour without component state: an inline intent stub, not a module (DOCS-ZERO 2026-10-27).** docs-kit `page-stub.ts` `PAGE_STUB` (written by `document.ts`; ~1.5 KB raw / ~0.44 KB br inline) imports the docs page script on the first pointerover / pointerdown / focusin / keydown / click / TOC scroll, queues those events for the module's `replay` and prevents the defaults that cannot wait (Ctrl/Cmd+K, `/`, ArrowDown on the menu button, search link click); it preloads the script's static imports with it (one round trip, not two). docs content pages: JS before input 1.9–3.1 KB br / 2 files → 0 (998 → 3 docs pages with JS before input); Lighthouse mobile FCP −75 ms, LCP −75–150 ms, −2 requests; HTML +0.42–0.45 KB br per view. Slow 4G + 4× CPU first theme click: after a 300 ms hover and cold Ctrl+K equal (≈ 0.8 s); a click with no pointer movement before it +78 ms (one round trip for the script). The external module was cached after the first page but parsed and ran on every view before input. Chrome closures (THEME-JS 2026-10-28): an event on a chrome button (theme / mobile menu, search + its shortcut keys) also modulepreloads that part's whole closure with the script (build-time lists `pageScriptParts()`), so the part's `import()` finds its files in flight: ui-docs theme menu, press with no pointer movement, 400 ms RTT: HTTP/2 830 → 430 ms (2 → 1 round trip), HTTP/1.1 2.89 → 2.47 s; HTML +0.86 KB br per view. Under HTTP/1.1 (local `serve`, the node adapter without a TLS proxy) the 53 files of that closure queue on 6 connections (7.2 round trips at 400 ms): measure cold interactions over HTTP/2, as production serves them.
- **Stateless motion and charts belong in CSS + server HTML (STATIC-ZERO-3 2026-10-27).** apps/docs home hero (replaced 2026-10-27 by the HOME-DOCS page: no motion, 0 scripts before input; its live counter is an iframe of the `ui-counter` example page since HOME-DOCS-2, which also fetches 0 JS before input and shows what its first press loads, docs-kit "JS meters"): headline word rotation (stacked words, one keyframe set, per-letter delays; each letter clips its own slice of the word gradient — Chrome's `background-clip: text` on a parent ignores children's transform / opacity / filter) + aurora blobs (`translate` / `scale` keyframes in container units), paused by a native checkbox (`:has(:checked)` → `animation-play-state: paused`): 1 file / 1.9 KB br before input → 0. `/about/benchmarks/` charts: marks placed by the server as CSS vars of their axis share (wide + narrow axis, `@container`), CSS hover tooltips, `view-timeline` entrance, keyboard in the docs page script: 21 files / 72.5 KB br → 0 (the canvas `visible` effect booted the runtime at load). docs-kit `/search/`: the `?q=` dialog opens from the page script, not a load-time effect: 18 files / 56.6 KB br → 0 (cdk-docs / ui-docs too). Slow 4G + 4× CPU (HTTP/2): theme click after a 300 ms hover and Ctrl+K equal; a press with no pointer movement before it +57 ms on /about/benchmarks (the runtime chunks the booted page had loaded now come with the menu, as on every DOCS-ZERO page); Tab + arrow on a chart 13 → 23 ms (keyboard module bundled into the page script: as a dynamic import it was 181 ms).
- **Lazy parts: split the closed state off, fetch the rest at idle (IDLE-PREFETCH 2026-10-27).** `lazyComponent(() => import(…))` parts reachable from a page's fetch-ahead list are the tail's `data-fl`: low-priority modulepreloads appended once every `data-fo` link loaded, in an idle callback (none under Save-Data / 2g), never evaluated before input; only such pages ship the +83 B br loader branch. ui-docs (cdk Popover inner, scheduler menus + `+N more` panel lazy): JS before input on pages ≥ 100 KB gz −4.7 % (top 20 −6.8 %, site −2.4 %; scheduler-views / month-features −26 %, popover-basic −10.7 %, select / date / color −4…−6 %; 97 pages +0.16 KB, the loader branch); fetched by idle +1.1 % vs base on those pages (2.85 MB gz `data-fl` over 211 pages: static, so scheduler-views fetches the menus it never renders). 150 ms RTT / 1.6 Mbps / 4× CPU, median of 5: hover 300 ms then press, after idle: equal (popover 31 → 18, select 15 → 13, date 89 → 88, colour 48 → 49, scheduler menu 14.5 → 17, month 35 → 40 ms); press with no pointer movement after idle +15…+60 ms (popover 46 → 62, select 63 → 113, date 187 → 247, colour 108 → 142, scheduler menu 101 → 133 ms: the part's import + module instantiate after the boundary ran, one more task before the mount); press before idle: popover pages +1 round trip (+150…+275 ms), scheduler-views −780 ms (less JS ahead of it). Evaluating the parts at idle would close the no-rest gap but breaks "nothing runs before input" (not done).
- **Cold states belong in CSS.** Pair `data-hovered` / `data-pressed` / `data-focus-visible` with `:hover` / `:active` / `:focus-visible` so the page looks right before its code runs (`libs/ui/tests-components/cold-states.test.ts` pixel parity) — except pressed transforms / scales / opacity: an `:active` rule changing those made the first adopt at pointerdown ~20 ms slower (checkbox-button-group 21 → 38 ms, number-stepper 23 → 47 ms fast); colour-only `:active` twins cost nothing measurable.

## Shipped bytes

Measured by lane DIET-CODE 2026-10-22 (size report, Playwright coverage of the cdk / ui story apps before input; spec `docs/design/specs/2026-10-22-chunk-merge-rule.md`).

- **Build-time evaluation instead of ports (COMPTIME 2026-10-25).** `rivet({ comptime })` runs real third-party / own code at build time: a constant call of an allowlisted or `@comptime` function becomes its result; a tailwind-variants definition becomes a lookup table proven against the library for every enumerated combination, and only modules that can call a resolver with a `class` / `className` override import the tailwind-merge registration (a static import from the table's module would put it in every page holding that chunk: rolldown places a module by reachability, not use). `@rivetjs/ui` does not adopt it yet (ruling 2026-10-26): on top of ZERO B3 (`@rivetjs/ui`'s own resolver) tables lose (frames +0.1…+4.5 KB gz) and the measured defer mode (`@comptime defer` on `tv.ts`'s `cn` import) saved 9.5 KB gz on 26 override-free pages but cost 924 pages +0.45…+0.68 KB gz (full ui-docs median 94.4 → 94.8 KB) — rejected as a median regression. The open lever is the override sites: slot components pass `{ class: local.class }` even when the caller sets no class, so most pages count as override pages; once an absent override is provable at the call site, defer mode becomes a net win.
- **Co-load chunk groups (BIG-UI-3 2026-10-27).** Rolldown splits shared code by the set of *entries* reaching it; a page loads several entries, so chunks reached by different entry sets are often fetched by exactly the same pages (runtime trio `derived-runtime` / `dom-derived-abi` / `resume-format` on 1030 ui-docs pages, `focus` / `focus-ring` / `hover`, …). docs-kit builds run two passes (router `build/coload.ts`, docs-kit `tools/coload.ts`): pass 1 is prerendered, `planCoload` groups non-entry chunks with the same before-input page set (a lean page's intent-only `data-fo` list counts as after input) and the same reachable page set (no page loads more, before or after input; no merge that closes a chunk cycle, through an outside chunk or another group), pass 2 builds the client with one `codeSplitting` group per plan entry (`includeDependenciesRecursively: false`). ui-docs: 314 chunks → 130, site JS before input −3.2 %, pages ≥ 100 KB −3.5 % (median 138.4 → 133.5 KB gz), 1030 pages smaller, none larger; files per big page 91 → 72; a click 1 s after load (before the idle fetch) at 150 ms RTT 645 → 351 ms, cold interactions equal. Cost: build +~45 s. Apps outside docs-kit can run the same protocol (env `RIVET_COLOAD`, `planCoload` from `@rivetjs/router/static`).
- **tailwind-merge on demand (ZERO UI-JS2 2026-10-26).** `@rivetjs/ui`'s resolver needs tailwind-merge only for an override it would change (not a fixed point); production browser builds start without it (`#tv-merge` → `merge-off.ts`) and the compiler (`libs/compiler/class-merge.ts`) adds `import "@rivetjs/ui/tv-merge"` to exactly the client modules that can make such an override (a literal like `w-96 w-full`, two utility parts joined, a value it cannot read). Server, dev and Node tests always merge, so SSR output is unchanged (ui-docs: 4,136 pages, class strings identical); the prerender probe saw 437 override merges, none changing the string. ui-docs: sum 99.2 → 90.7 MB, median JS frame 98.9 → 89.2 KB gz (−9.7 KB on 880 frames), the 35 frames that need the merge +0.2…0.5 KB. Holes (rule them before relying on a merge in the browser): class strings from run-time data (JSON, a loader) read through a class-like key, and record-shipped props a module computes on the server that the browser never loads — both reach the resolver unmerged. `cx` is ui's own port (tailwind-variants' shares its module with tailwind-merge; one module = one chunk). Prop joins (BIG-UI-3 2026-10-27): a value that only joins two forwarded class props of the exported component it sits in (Scheduler: `[local.classNames?.base, local.class].filter(Boolean).join(" ")`) is a source only when a caller passes two of them; co-load builds (`RIVET_COLOAD`) decide it across their passes (pass 1 records every client module's uses in `class-joins.json`, pass 2 imports the merge into the component's module only when a caller may pass two, or a use it cannot follow: spread, value use, `import.meta.glob`); one-pass builds keep it a source. Local render-only components (`<SchedulerHeader classNames={…}>` that only put the value on intrinsic `class`) are no origins. ui-docs: 15 Scheduler frames −10.2 KB gz each (165.6 → 155.4 KB), merge on 35 → 20 frames, HTML identical.
- **Locale tables: only the declared languages (ZERO UI-JS2).** cdk string tables carry 34 react-aria locales. An app that declares its locales (`rivetRouter({ locales })` / `rivet({ locales })`, else `i18n()` `locales`) ships, in production client builds, every key of those languages + `en-US` per `// @rivet-locale-table` export; a lookup in another language loads the whole table (own chunk) and renders `en-US` strings until it lands — so list every language served. Undeclared (default, ruling 2026-10-26): whole tables, exact for any locale. Keeping whole languages keeps every lookup exact (first key of the language in source order). The docs sites and starter-ui declare theirs; ui-docs: date pickers −9.8 KB gz, combobox / select / color pages −1…−8 KB.
- **Static variant classes (VCLS 2026-10-28).** A ui component that declares `// @rivet-class Comp(classProps) resolver with(contexts)` (today: Button) reads a precomputed `$cls` at call sites whose class props are constants (literals / absent; no `class`, `className` or spread): the build runs the real resolver in the comptime worker (`libs/compiler/static-class.ts`). When no module of the build has an unproven site (a variable variant, an override, a `ButtonGroup` context import, a value use, a dynamic import, JSX in a helper), the browser build reads the resolver lazily from a registry nobody fills: the variant table never ships, and ui's `tv` resolver leaves too unless another shipped component still uses it (then the effect module keeps it reachable from button, so no other module changes chunk). Per build, not per page: in a multi-entry build a module leaving some entries re-lays the chunks it shared — per-page proof (`RIVET_STATIC_CLASS=page`) on the frame gate: Button-only frame −842 B br, eight mixed frames +274…+641 B br (+1–2 files); on apps/docs ui-counter −1,037 B br but home +76 / ProductShot +178 B br (+1 file); dropping a shared `tv` split `cx` into its own chunk on starter-ui (+58 B br). Shipped (same-commit A/B, client builds): apps/docs ui-counter 16 → 15 files, 34,753 → 34,588 B br (−165: no `button.styles`; `tv` kept, the home Card shares it), home route 33 → 32 files, −107 B br, ProductShot identical; starter-ui −73 B br; the 17 frame-gate frames byte-identical (ui-docs has unproven sites); a build whose runtime is unshared drops both (ui-counter on the full-drop path: −987 B br, `live` 1,338 → 497 B br). SSR markup identical, cold matrix 8/8. Cost on every Button page: the `$cls` branch, +37…59 B br. `RIVET_STATIC_CLASS=0` = off.
- **One fetch-ahead file for a one-lite-module app (JS-DIET-2 2026-10-28).** The lite runtime and the only lite entry share one chunk (Rolldown `codeSplitting.groups` from the plugin's `outputOptions`, roots set at `buildEnd`): starter-static / tutorial-03 2 → 1 request, 2,622 → 2,423 B br before input; real pages with stand-in residuals 3.6–5.1 → 3.2–4.5 KB br. A default-exported lite boundary keeps the runtime's ~90 B facade file (the chunk's `default` would be the runtime, which the full runtime's fallback reads as the component): 2 requests, still −100..−285 B br (counter 2,639 → 2,530). Several lite entries keep separate chunks (no duplicated runtime). Do not add the group from the `config` hook as `environments.client` options: that changed other builds' output (docs motion examples' Tailwind CSS grew). Changing `dom-derived.ts` to tell lite chunks by `<Name>$c` instead was measured too: −9 B min but +80..+190 B br on every ui-docs frame (Brotli), so the compiler avoids the collision instead.
- **Evaluating the runtime at idle did not pay (JS-DIET-2 slice 4, measured, not landed).** `import(data-rt)` in an idle callback once its modulepreload loaded: real pages first click input→mutation / paint unchanged within noise (e.g. products slow 28.0 → 27.1 ms mutation), +13 B br loader. The lite runtime's evaluation is too small to see; the first click is dominated by the first-mouse-click deferral and the adopt itself.
- **Named imports, not `* as M`, for server-only module data.** A namespace import makes rolldown build a namespace object (`__exportAll`, its `rolldown-runtime` chunk: +1 request); the docs frame modules import `head` / loaders by name behind `import.meta.env.SSR` (components excluded: a value reference makes them escape the site analysis), and a dynamic `import()` of a statically shared module goes through its own lazy entry (`cdk/announcer/announce-lazy.ts`). ui-docs: `rolldown-runtime` gone from 867 frames (−1 request, −0.26 KB gz median). Keep namespace-using libraries out of lazy entry chunks: rolldown merges its runtime into an entry chunk that already uses it (`chunkOptimization.mergeCommonChunks`), so every chunk with a namespace object imports that entry statically — the docs highlighter entry (Shiki's `property-information` namespace, 189 KB) was imported by 202 docs chunks incl. the search palette; docs-kit `docsChunks` moves Shiki into a non-entry `highlighter-core` group chunk and the runtime stays its own 187 B chunk (SEARCH-CHUNK: cold Ctrl+K 223 → 34.7 KB). A codeSplitting group cannot capture `\0rolldown/runtime.js` itself.
- **`cx` from `tailwind-variants/lite`.** Same function object as the root entry's `cx`, but the root import keeps `tailwind-merge` reachable; `libs/ui` imports `cx` from `/lite` everywhere it only joins classes. Alone: starter-ui eager 62.75 → 62.61 KB br: `cn` (merge) still needs the root. Dropping merge from the eager path would be −8.3 KB br (62.75 → 54.42) but needs a sync merge on client renders — no lazy path without a semantic change. ZERO B3 (2026-10-25): ui's own `tv` resolver (no tailwind-variants `tv` runtime) + a build-time split of tailwind-variants' `index.js` (merge module vs `tv` runtime, compiler `_pureAnnotate`): ui frames −2.2…−3.5 KB gz each (full ui-docs build median 101,038 → 98,691 gz, 955 pages); tailwind-merge itself (10.6 KB gz) stays for the same reason. ui `cx` now comes from `styles/src/utils/tv.ts` (not `/lite`).
- **Gate dev-only code with the `#dev` constant, not a runtime check.** `if (DEV)` folds to nothing in production; a runtime `process.env.NODE_ENV` check (the `isDev()` helpers the React Aria ports carried, deleted 2026-10-22) ships the warning text and its helpers (cdk: warn text 2762 → 1053 B over the story app, `/button` 87.2 → 85.2 KB br). Caveat: inside a `.tsx` closure that the compiler extracts as a resumable symbol the body still ships (symbols are built before constant folding) — keep warnings in plain functions. Never import a module by name only for DEV-guarded code: Rolldown decides inclusion before folding `DEV = false`, so the module stays as a bare import (lane DIET-CONST); route dev hooks through the `#dev` object (`DEV.hook(…)`).
- **Put resume-only helpers in their own module.** A client build places a module in one chunk; a helper exported from a hot module (reactivity `index.ts`) ships in the eager chunk even when only a lazy chunk calls it. `_trackReads` moved to `@rivetjs/reactivity/track`: eager runtime of lazy-row apps −1.26 KB min / −0.34..−0.41 KB br.
- **A top-level call is never tree-shaken.** `const EMPTY = Object.freeze([])` stayed in every bundle that imported reactivity (18 B min each) until it moved next to its only user.

## Rendering (style / layout / paint)

Measured by lane RENDERCOST 2026-10-26 (`apps/dom-bench/render/`: main-thread self time per phase from Chrome traces, Chrome 155, macOS, 1× and 4× CPU; numbers in `docs/benchmarks/2026-10-26-rendercost.md`).

- **Rivet's DOM writes already cost what vanilla's cost.** krausest 01–09: Rivet and vanilla recalculate the same elements and lay out the same objects (01_run1k 9,001 / 12,007 both); style + layout + paint within noise on every benchmark at 1× and 4×. The gap is script (+0.5 ms on 01). Nothing in the DOM write shape left to win there.
- **Hole / boundary comments cost no rendering.** Static ui frames with all comments stripped (kanban 422 comments, scheduler 376) vs as served: load style / layout / paint equal within noise. Removing markers is a bytes / adopt question, not a rendering one.
- **Per interaction, rendering is small and mostly browser work.** ui frames at 1×: 0.8–3.5 ms render per click (kanban move 1.3, scheduler next 1.3, data-grid sort 3.0, table select-all 1.3); single attribute toggles (`data-hovered`, `data-pressed`) cost 5–25 µs of style. Style cost per interaction scales with newly inserted / moved elements (5–8 µs each), not with selector matching: Chrome selector stats on kanban total ≈ 0.6 ms over load + 4 clicks. In ui CSS, rules whose subject is an attribute (`[data-slot="…"]`) are ≈ half of a full forced recalc (they share Chrome's attribute-name bucket); no `:has()` rule measurably costs. A text change inside a 500-item CSS grid (zero-cards) re-runs grid layout: 0.5 ms (1×) / 2.2 ms (4×) of a 0.9 / 4 ms render, script 0.09 ms — author CSS, not framework output.
- **Cold first layout pays for the font stack (Chrome, macOS).** A miss in `font-family` costs a CoreText lookup in the first layout of a renderer (not CPU-throttled): `-apple-system` first = +2.2 ms vs `BlinkMacSystemFont` / `system-ui` first; a stack of absent families before Arial +3.7 ms. Tailwind 4's default `--font-sans` starts with `-apple-system`. `BlinkMacSystemFont, -apple-system, …` is pixel-identical in Chrome and cuts frame load rendering 15–20 % at 1× (kanban 11.5 → 9.7 ms), but costs WebKit ≈ +1.5 ms (its own miss on `BlinkMacSystemFont`): not adopted (ruling pending). `system-ui` first is fast everywhere but resolves to a different font on Linux / CJK Windows.
- **`content-visibility: auto` on long docs pages is a big load win but not pixel-exact.** `.prose > :is(.example, .code-block, .table-wrap)` with `contain-intrinsic-size: auto 400px`: ui-docs component pages −15…−25 % load rendering at 1× (table 61 → 46 ms, scheduler 65 → 52 ms), −10…−23 % at 4×. Paint containment snaps the contained subtree to whole pixels: text anti-aliasing and ≤ 1 px offsets differ in screenshots (`render/parity.ts`), so it fails strict screenshot parity; not adopted (ruling pending). It never helps a framework-rendered list: each row's containment is author CSS and the framework cannot prove it safe (overflow, out-of-flow descendants, sub-pixel offsets).
