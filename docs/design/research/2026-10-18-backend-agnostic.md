# One IR, many executors — backend-agnostic rendering as a consequence of the derived client (2026-10-18, round 4)

- Status: research note, lane RESUME-V2 round 4 (user: "what if we were backend agnostic — Go, Rust, ASP.NET, Python; we only care about everything else: resuming, interactions"). No code. Roadmap placement is the user's call (§6).
- Short answer: it is the natural consequence of the derived client (`2026-10-18-beyond-resume-hydration.md`) and it subsumes the native host of round 3 (`2026-10-18-floor-first.md` F4). Serialized resume can never be backend-agnostic (the server must execute JS closures to record the graph); hydration cannot either (the server must run the same JS components). The derived client moves all *structure* into the compiled browser program; what a server must produce is HTML from a template, a small JSON values tail and marker attributes — which any language can emit.

## 1. The product

The compiler emits, from the same JSX source: (a) the browser program (derived slices, adopted-layer chunks, loader) as designed; (b) a **portable template IR** for the server: a segment table (static byte runs) plus a small instruction program — loops over data, conditionals, text / attribute holes with a restricted expression language, boundary / structural markers, the values tail. Each backend gets a thin **executor** library (hundreds of lines: Rust, Go, C#, Python, and the existing Node one): data in, HTML + values out, resumable in the browser. Actions and data loading stay the backend's own, under a documented HTTP contract (form posts / fetch; a patch response = fragments rendered by the same executor + values). Rivet stops competing on "a fast Node server" and competes on "your server, any language, a compiled UI with resumable interactivity" — a space held today only by hypermedia tools (HTMX / Datastar) with no state model and no compiled client.

Round 3's op-stream (F1), native writer (F2′) and native host (F4) collapse into this: **one IR, many executors**. The Rust executor is the ceiling (the 2026-10-06 spike: 3.3× Node's CPU / page, 20× less memory); Go close; .NET competitive (the Razor comparison becomes "Rivet templates inside ASP.NET render faster than Razor and resume"); Python slower but usable; the edge executor (F5) is the Rust one on Workers.

## 2. Three server tiers, chosen per component by the compiler

| Tier | What renders it | When | Cost |
| --- | --- | --- | --- |
| **portable** | the IR executor, native speed | the component's server render fits the expression subset (§3) | the floor (native) |
| **sidecar** | an embedded JS engine (QuickJS bindings exist for Rust, Go, C#, Python) running only that component's compiled server function on props JSON | real server logic the subset does not cover (cdk collections, id / ARIA wiring with computation) | ~µs–ms per component; no process boundary |
| **browser** | the rendered layer after load | client-only components (`clientOnly`, islands) | as today |

The interaction map (round 2) gains a server column: tier per component and the construct that decided it. No author annotation; an author who wants a component portable removes the construct the report names.

## 3. The expression subset (first cut; the spike decides the exact line)

Allowed in portable templates: member access on data / props / loop variables, literals, arithmetic, comparisons, logical and nullish operators, ternaries, template literals, `.length`, `.map` / `.filter` / `.find` / `.includes` / `.join` with arrow bodies in the subset, a fixed helper set (`String` / `Number` conversions, `toLowerCase` / `toUpperCase` / `trim` / `slice`, `Math.min` / `max` / `round` / `floor`), ICU formatting (dates, numbers, plurals — already compiled per locale by `@rivetjs/i18n`), `createId` (per-render counter), `class:` / `style:` lowering. Not allowed (→ sidecar): calls to user or library functions outside the subset, `new`, regex, `Date` arithmetic, closures stored in data, context providers whose values hold functions, anything that reads a signal through a helper. Initial values of keyed signals must be in the subset too (or static defaults) — they are the values tail.

Semantics are pinned by a **conformance corpus**: every compiler corpus case plus every cdk / ui story rendered by every executor must be byte-identical to the Node executor (the oracle corpus infrastructure exists; numbers, strings and Unicode are where executors drift).

## 4. The contract (what a backend implements)

1. Load the route's IR (JSON, generated by the compiler at build time) and the generated data types (TypeScript props → JSON Schema → Go structs / C# records / Python `TypedDict` / Rust structs; generated, never hand-written).
2. For a request: run loaders in the backend's own way, call `render(route, data)` on the executor → HTML stream with markers + values tail + the inline loader; serve the compiled client assets as static files with the dictionary headers (`Use-As-Dictionary`, F3) from generated config.
3. Actions: a documented endpoint shape; the client's derived slice posts and applies the patch (fragments by boundary id + values) rendered by the same executor.
4. Trusted HTML from the backend (markdown rendered in Go): a `TrustedHtml` value type the contract allows only from the server side, never from client data.
5. Streaming (`Async` / `Suspense` segments): optional per executor; the IR marks boundaries; a non-streaming executor renders in order.

## 5. Risks, honestly

- **The subset line.** Too narrow → application components fall to the sidecar constantly; too wide → N executors with drifting semantics. The spike (§6) measures the first and the conformance corpus guards the second.
- **cdk / ui on non-JS backends.** Widget server renders compute ids, ARIA wiring, collection items. Expect a split: markup-only parts portable, a JS core on the sidecar. The sidecar makes "every component works on every backend" true on day one; portability of widgets improves over time as the report names constructs.
- **Maintenance.** Five executors is five codebases; they must stay tiny (the IR does the work) and be generated-test-driven. Community ownership per language is realistic only after the Node and Rust executors are the reference.
- **Dev experience.** `rivet build` must produce a complete artifact for the backend (IR + assets + types + config) and `rivet dev` must proxy a foreign backend; the Vite dev server stays for the JS-backed path.
- **Scope.** This is a product-line decision, not a perf lane. It does not change the browser side at all, which is why it can be decided after S2 (passed, `2026-10-18-beyond-resume-hydration.md` §12) without touching that work.

## 6. The spike that decides (2 days, compiler facts only)

**P1 portability classifier**: run the compiler's corpus, every cdk and ui component, the three docs apps, the starters and the bench apps through a classifier over the existing facts (server-target IR, imports, calls, `new`, helper use): per component → portable / sidecar / browser, with the deciding construct. Report: share of components per tier for application code vs widget libraries, the top constructs that demote, and the IR size per route. Bar: ≥ 80 % of application components portable; widget libraries with a nameable JS core (≤ 20 % of their components on the sidecar, and those by a short list of constructs). If met, the executor work starts with Rust (reference, also the edge executor) and Node (existing), then Go / .NET; if not, the subset is redrawn once and the spike re-run.

Rulings (user): **R-F** adopt backend-agnostic rendering as a direction (on the roadmap as "idea → planned" after P1) vs keep it a research note; **R-G** executor order (recommendation: Rust + Node reference, then Go, then .NET, then Python); **R-H** the sidecar is a first-class tier (recommendation: yes, it is what makes the promise true on day one).
