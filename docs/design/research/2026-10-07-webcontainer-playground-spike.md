# WebContainer playground spike — can a Rivet starter boot + hot-reload in the browser? (2026-10-07)

Question: run a Rivet starter (`templates/starter-static`: Vite 8 + `@rivetjs/router/vite` + 3.1 MB compiler wasm + Tailwind 4) inside a WebContainer (`@webcontainer/api` 1.6.4, runtime `d5306e6f`) for an `apps/docs` playground + tutorial. Throwaway code: session scratchpad `webcontainer-spike/` (host page + Playwright drivers; not committed). Packages from `nx run-many -t package` (`dist/libs`, `npm pack` tarballs). Measured in headless Playwright Chromium / WebKit / Firefox (repo `playwright` 1.63) + the desktop built-in browser (Chromium 152, pane hidden), host page on `localhost:4410`.

## Verdict

- **Yes, viable for Chromium + Safari (WebKit)** — dev server, SSR, resume, click handlers, route/component HMR, `vite build` + `--ssr` + prerender all work on the container's Node 22.
- **Two blockers in our code/stack, both small:**
  1. Router dev server always sends the strict nonce CSP (`script-src 'nonce-…' 'strict-dynamic'`) → blocks WebContainer's injected preview runtime (`/.webcontainer@runtime.<hash>.js`) → Vite HMR websocket fails (404), page never updates. Needs a router change (see Blockers).
  2. Tailwind 4 in WebContainer does not pick up **new** class names until the dev server restarts → playground/tutorial templates should not use Tailwind (use plain CSS / Rivet scoped styles).
- **Must ship a prebuilt `node_modules` snapshot** (in-container `npm install` = 24 s + 10 s rolldown wasm download; snapshot boot = 3.5–7.7 s to first preview).
- StackBlitz SDK embed: not usable today (packages not on npm; embeds refused in headless Chromium). Keep as "Open in StackBlitz" link after publishing.

## Findings per question

1. **Node version** — container = Node 22.22.3; `engines >=24` only produces `npm warn EBADENGINE` (not fatal; `engine-strict` is off). Everything exercised ran on 22: Vite 8 dev + build, router SSR/resume/prerender, compiler wasm, Tailwind, sharp. Node 22.22 has type stripping on by default. Static scan of `dist/libs/**` for Node-24-only APIs: only `Error.isError` (devtools, already guarded). Not exercised: `rivet-check`/language-core/typescript-plugin, `starter-server` node adapter (`serve.js`). Workarounds: none needed beyond accepting the warning; optionally drop `engines` from the playground template's `package.json` only. Repo engines unchanged.
2. **Native deps** — no workaround needed on install: the WebContainer npm mirror swaps `lightningcss` → its wasm build and `@tailwindcss/oxide` → the wasi build; rolldown (Vite 8) detects WebContainer and `pnpm i @rolldown/binding-wasm32-wasi@<ver>` into `/tmp/rolldown-<ver>` on first start (10 s, prints `[rolldown] Downloading …`). It resolves `@rolldown/binding-wasm32-wasi` from `node_modules` first, so vendoring it (+ `@napi-rs/wasm-runtime`, `@emnapi/{core,runtime,wasi-threads}`, `@tybys/wasm-util`, `tslib`; version must equal rolldown's) into the snapshot removes the download. esbuild: not installed by Vite 8 (not needed). sharp: `@img/sharp-wasm32` selected automatically, works. Node prints `ExperimentalWarning: WASI` per wasi load (cosmetic; filter in the terminal UI).
3. **Unpublished packages** — `npm view @rivetjs/runtime` → 404. Snapshot approach that works: build it **inside a WebContainer** (host `npm install` would give darwin natives): boot → mount template + `dist/libs` tarballs (`file:` deps + `overrides: { "@rivetjs/x": "$@rivetjs/x" }`) → `npm install` → copy the rolldown wasi binding into `node_modules` → `rm node_modules/.vite` → `wc.export("node_modules", { format: "binary" })`. `@webcontainer/snapshot` (host-side) not used for that reason.
4. **Compiler wasm** — loads unchanged (`readFileSync` + `new WebAssembly.Module`, no WASI). Steady compile speed = host; first process in a fresh profile tiers up (≈ 34 ms/compile for 117 KB), later processes hit the browser wasm code cache. First SSR request after `server-ready` ≈ 1–2 s including route compile + Tailwind scan.
5. **Headers** — `crossOriginIsolated` needs COOP `same-origin` + COEP on the host page.
   - Chromium (Playwright): `require-corp` ✓ and `credentialless` ✓. Built-in desktop browser: `require-corp` ✓, `credentialless` preview iframe stayed blank.
   - WebKit (Playwright ≈ Safari): `require-corp` ✓ (full flow incl. HMR); `credentialless` unsupported → not isolated → `boot()` throws `DataCloneError`.
   - Firefox (Playwright): isolated with both, container + Vite run, but the preview iframe never requested the page (no paint, no HMR) — matches docs "beta"; treat Firefox as fallback.
   - Docs (StackBlitz browser-support page): Chromium full; Firefox beta (preview third-party assets may be blocked; no Private Browsing); Safari ≥ 16.4 beta; Android/iOS beta with memory limits; embeds Chromium-only.
   - → use **`require-corp`** (only mode that works in Chromium + Safari); boot with `{ coep: "require-corp" }`; preview origin `*.local-corp.webcontainer-api.io`.
   - Preview iframe: `allow="cross-origin-isolated"` (angular.dev does the same). Opening the preview in a new tab redirects to **`/webcontainer/connect/<token>` on the host origin** — the docs site must serve a page there calling `setupConnect()` from `@webcontainer/api/connect` (else 404).
6. **Licensing** (webcontainers.io/enterprise): no license needed for prototypes/POCs; "Licensing is required for _production_ usage of the API in a commercial, for-profit setting." Open-source framework docs = not for-profit customer use → free; re-check if the docs ever sit under a commercial entity's product site.

## Blockers + workarounds

- **Router dev CSP vs WebContainer (must fix before shipping)** — `libs/router/build/vite.ts` dev `createApp({…})` passes no `csp`, so `server/app.ts` defaults to `nonceCSP`; WebContainer injects its preview runtime `<script>` without our nonce → blocked → Vite client cannot open its websocket (`404` on `wss://…webcontainer-api.io`, fallback `wss://localhost:5173` refused). Spike workaround: a Vite middleware that drops `content-security-policy` before `writeHead` → HMR works. Proposed fix (router lane): `rivetRouter({ dev: { csp } })` passthrough and/or dev CSP off when `process.versions.webcontainer` is set; the playground template can then opt out explicitly.
- **Tailwind incremental scan** — new utility classes never reach the CSS (both `wc.fs.writeFile` and in-container `fs.writeFileSync`; touching `styles.css` doesn't help); dev restart fixes it. Workaround: Tailwind-free playground/tutorial templates (also −13 MB snapshot). Not root-caused (suspect the oxide wasi scanner's change detection).
- **First edit right after first paint** — an edit within ≈ 2 s of first paint produced only `(ssr) page reload`, no client update (client module graph not yet populated while resume chunks load); later edits HMR in 24–64 ms. Workaround: editor marks "ready" after the first client `vite:afterUpdate`/load, or reloads the preview iframe if no update lands within ~1 s.
- **Snapshot export gotchas** — export drops `.bin` exec bits → spawn `node node_modules/vite/bin/vite.js` (`npx vite` → `EACCES`); ship `package-lock.json` with the template (a later in-container `npm install` without it fails `EBADPLATFORM` on `@tailwindcss/oxide-wasm32-wasi`); strip `node_modules/.vite` (else "Re-optimizing dependencies").
- Aside (not WebContainer-specific): after a route/component HMR the counter shows `0` again on host and in the container, although the template text says the count is kept — check with the router/resume lane.

## Recommended architecture (apps/docs playground + tutorial)

- **Routes + headers**: COOP `same-origin` + COEP `require-corp` only on `/playground/**`, `/tutorial/**` and `/webcontainer/connect/**` (docs `tools/serve.ts` + production host header config). Full page loads into those routes (`data-rivet-reload`). Every subresource on them same-origin (self-hosted fonts, Pagefind, images) or sending CORP.
- **CSP on those routes**: `script-src 'self'` (+ nonce/hashes as today); `frame-src https://stackblitz.com https://*.webcontainer-api.io`; `connect-src 'self'` (snapshot fetch); `worker-src 'self' blob:` if the editor uses workers; no `'unsafe-eval'` needed on our page (the runtime lives in the cross-origin headless iframe).
- **Snapshot build step** (new docs-kit tool, e.g. `tools/webcontainer-snapshot.ts`, run in docs build/CI): Playwright Chromium → local page → boot → mount template + `dist/libs/*` tarballs → `npm install` → prime rolldown → vendor the wasi binding → drop `.vite` → `export` binary → `public/webcontainer/<template>.<hash>.bin`, served brotli + `immutable`. Rebuild when `dist/libs`, template lockfile or rolldown version changes. One snapshot per template (~11 MB br with Tailwind, ~9 MB without); tutorial steps share one.
- **Runtime**: module singleton `WebContainer.boot({ coep: "require-corp", workdirName })` on intent (route enter / hover "Run"), snapshot fetch in parallel; mount `node_modules` once; per tutorial step mount/write only changed files (no server restart); spawn Vite via node path; preview `<iframe allow="cross-origin-isolated">`; terminal/console via `spawn` output; `teardown()` only on leaving the route.
- **Templates**: dedicated playground template derived from `starter-minimal` (no Tailwind; plain CSS or Rivet scoped styles; devtools optional, −10 MB), with `package-lock.json`; tutorial steps = file overlays on it.
- **Editor**: CodeMirror 6 (`@codemirror/lang-javascript` JSX+TS, own theme from brand tokens), lazy-loaded on the isolated routes only; debounced (~150 ms) `wc.fs.writeFile`; diagnostics from `@rivetjs/compiler/editor` in the host page possible later. Bundle size not measured in this spike.
- **Unsupported/mobile fallback**: when `!crossOriginIsolated`, Firefox, or viewport < 768 px → read-only code (highlighted) + live prebuilt example iframe from the existing examples origin + "Open in StackBlitz" (once packages are published) — never block the tutorial text.
- **StackBlitz SDK fallback (evaluated)**: `sdk.embedProject` (SDK 1.11.1, `template: "node"`) needs packages from npm (files are strings → no tarballs) → blocked until `@rivetjs/*` is published. A stand-in Vite + Tailwind project in headless Chromium: without host headers the embed shows "Unable to run Embedded Project … without proper isolation headers"; with COEP on the host the embed iframe is blocked. Docs: embeds Chromium-only; Node runtime is the same WebContainer (expect Node 22). Use only as an external "Open in StackBlitz" link.
