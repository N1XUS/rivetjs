# editorial-bench

Question: is Rivet better than editorial-site frameworks for editorial websites? Same content, same CSS, same markup, six static lanes + one dynamic Rivet lane, one shared static server. Results: `results/report.md` (generated), write-up `docs/benchmarks/2026-10-11-editorial.md`.

## Site

Generated by `fixture/gen.ts` (seeded mulberry32, byte-identical per N): N articles (100 / 1000 / 5000), Markdown with JSON-literal front matter (`slug`, `title`, `date`, `author`, `authorSlug`, `tags` 2–4 of 20, `description`, `related` 4 slugs), 3–6 KB bodies (h2/h3, paragraphs with strong / em / code / internal + external links, two images, a list, an ordered list, a JS code block, a blockquote). `site.json`: 20 tags, 12 authors, 20 per index page, 50 per tag / author page.

Pages (every lane, same URLs, directory form): `/`, `/page/N/` (20 teasers + pager), `/articles/<slug>/` (title, byline, tags, body, related rail of 4), `/tags/<tag>/` and `/authors/<slug>/` (50 newest). `<head>`: charset, viewport, `<title>X | The Daily Fixture</title>`, description meta, `<link rel="stylesheet" href="/site.css">`. Shared `fixture/site.css` (2.3 KB, system fonts) and 4 JPEGs (`fixture/assets`, copies of `apps/ui-docs/examples/_assets/cover-*.jpg`, 480×480, 16–26 KB).

Each lane: `lanes/<lane>/{package.json, package-lock.json, build.sh, README.md}`; `build.sh <abs fixture dir>` writes the deployable site (rivet: `dist/client`, others: `dist`). Rivet resolves `@rivetjs/*` + Vite from the repo root.

## Fairness rules

- Same fixture files, same HTML structure per page type, same stylesheet, same image files and URLs; `run.ts` checks visible body text of 20 article pages against Rivet per lane ("content parity").
- Same Markdown library (marked 18.1.0) in every JS lane; Hugo uses Goldmark with highlighting, typographer and heading ids off.
- No image pipeline in any lane (plain `<img>` from `/img/`), no syntax highlighting, no fonts.
- No framework prefetch / islands: Astro `prefetch: false`, no integrations; Next plain `<a>` (no `<Link>` prefetch); SvelteKit `data-sveltekit-preload-data` removed; Rivet `<a>` (static mode: the client router ships only on pages that resume something else, `clientRouter` default — none here, so links load documents).
- Framework defaults otherwise kept (that is what a user gets): Rivet's zero-JS static pages (no loader, client router or `_data.json` when nothing resumes; before 2026-10-12 every page shipped them), Next's React runtime + RSC payloads, SvelteKit's hydration + inline data.
- Serving: one Node server for every lane (`harness/static-server.mjs`: serve-static 2.2.1 + compression 1.8.1 gzip, `Cache-Control: no-cache`). Framework servers are not used.
- Builds start clean (each `build.sh` deletes `dist`, caches and generated dirs); 3 valid runs per lane and N, interleaved by lane.

## Deviations (recorded)

- Astro: brief named Astro 5; latest stable on 2026-10-11 is 7.3.8 (used). Bodies via marked, not Astro's remark `render()` (same library as the other JS lanes; Astro's default would add its remark pipeline to build time).
- Hugo: Goldmark, not marked. Writes an extra `/page/1/` alias redirect file. Taxonomy key `authorslug` (front matter key, case-insensitive) for author pages.
- Eleventy: articles are copied into its input dir by `build.sh` (counted in build time).
- Rivet: `.server.ts` naming not used for the content module (a rolldown 1.2.12 race fired the router's server-only guard at random; fixed in 2d198ad1, see CLAUDE.md); the module is only imported by stripped `serverLoad` / `serverEntries`.
- Rivet has no raw-HTML sink: Markdown is rendered from marked's token tree as JSX (`components/Markdown.tsx`); element structure matches marked's HTML renderer.
- SvelteKit 3: config in `sveltekit({...})`, `$lib` → relative imports (Kit 3 removed both).
- Next writes `out/`; `build.sh` moves it to `dist/`. Default build workers exceed the 2.8 GB cap at N ≥ 1000 (reported `over-cap`); `NEXT_CPUS=<n>` sets `experimental.cpus` for a reduced-worker variant (`run.ts --as <key>`), probed only (see the write-up).

## Metrics (`run.ts`)

- Build: wall time and peak RSS of the build process tree (`ps` sum every 50 ms, max'd with `/usr/bin/time -l` max RSS) per N; median (min–max) of 3 valid runs; a run is void when the 1-min load at its start is above `--max-load` (8); end load recorded. Builds above 2.8 GB tree RSS or 20 min are killed and reported as `over-cap` / `timeout`.
- Output: total bytes and files of the site root, JS files, article HTML raw / brotli q11 / gzip (median of 20 articles), inline JS, inline data scripts, referenced JS (script src + modulepreload) per article.
- Browser (N = `--serve-n`, 1000): JS actually loaded by an article page (Playwright Chromium, 4 s idle after load), Lighthouse 13.5.0 mobile preset (3 runs, article + index; LCP, FCP, TBT, CLS, score), DOM elements, cold-cache Playwright navigation at Fast 3G (562.5 ms RTT, 1.44 Mbit/s) + 4× CPU (5 runs: DCL, load).
- Dynamic: rivet-dynamic (node adapter) vs the shared static server on the same 20 article URLs, closed loop c1 / c10 for 10 s each, 3 rounds: p50 / p99 latency, TTFB, rps, server CPU ms per request (`ps` time delta). The client is `apps/ssr-bench/loadgen/client.ts` `Connection` (keep-alive raw HTTP/1.1); the ssr-bench loadgen itself validates its own page format only, so it cannot target these URLs.
